# Documentation Clarity

AI が書く文章の品質基準。PR / issue / コードコメント / Markdown に適用する。

読み手は、この変更の背景も、チームの事情も知らない人だと考える。
その人が読んで分かる文章だけを残す。

## 適用範囲

| 対象                     | 適用タイミング         |
| ------------------------ | ---------------------- |
| PR のタイトルと説明      | 作成時と更新時         |
| issue のタイトルと説明   | 作成時と更新時         |
| ソースコード中のコメント | その変更の差分の範囲内 |
| Markdown ファイル        | その変更の差分の範囲内 |

差分の外は書き換えない。無関係なファイルの整形は別の変更として扱う。

## 1. 識別子を書かない

ソースコードと Markdown に次を書かない。

- issue 番号 / PR 番号（`#123`, `GH-123`）
- チケット ID、レビュー ID、スレッド ID
- プロジェクトやチームにしか通じない呼称・略号

背景の説明が必要なら、番号ではなく背景そのものを一般的な言葉で書く。
番号やリンクの置き場所は commit message / PR / CHANGELOG。

## 2. 経緯を書かない

検討や実装の過程で起きたことは成果物に残さない。

- 「当初は X だったが Y に変更した」
- 「レビュー指摘を受けて修正」
- 「暫定的に Z としている」

書くのは、現在の仕様と、そうである理由だけ。
過程は git history と PR に残る。二重に書かない。

## 3. 削る

- 自明な記述を消す。
- 同じ内容の繰り返しは 1 箇所にまとめる。
- 冗長な言い回しを短くする。

判断基準は「消しても読み手が困らないか」。困らないなら消す。

## 4. 平易に書く

- 一般的な用語だけを使う。造語と内輪の言い回しを避ける。
- 一文一主張。文を短くする。
- 適度に改行し、1 行を読みやすい長さに保つ。

## 5. 視覚的に整える

- 並列する項目は箇条書きにする。
- 3 項目以上の対応関係は表にする。
- 順序のある操作は番号付きリストにする。

## 6. 書き終えたら読み直す

変更した箇所を全件読み直し、次の 2 点を確認する。

1. 分かりにくい言い回しが残っていないか
2. 翻訳調になっていないか

AI の思考言語とリポジトリの記述言語が違うとき、直訳の痕跡が残りやすい。
これは言語の組み合わせを問わず起きる。
その言語の書き手が普通に選ぶ語順と語彙に直す。

## 自動リマインド

`.claude/settings.json` の hooks が、次の 2 つの場面でこの基準を読み込ませる。

| 場面                                              | hook        |
| ------------------------------------------------- | ----------- |
| GitHub MCP ツールでの PR / issue / レビューの投稿 | PreToolUse  |
| Markdown ファイルの書き込み・編集                 | PostToolUse |

hook は `node` を直接起動して固定文を出力するだけで、
シェルもファイル読み込みもネットワークも使わない。

`gh` コマンドは対象外。Bash 向けの条件指定は、複合コマンドに対して
意図せず一致する。基準そのものは `CLAUDE.md` と `AGENTS.md` から
常に読み込まれるため、`gh` を使う場合もこの基準は適用される。
