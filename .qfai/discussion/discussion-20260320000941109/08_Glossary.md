# Glossary

| Term                        | Definition                                                                                                                                                                                                                      |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **TDDCycleController**      | Sub-agent that orchestrates the TDD micro-cycle and enforces item ordering. Responsible for selecting the next TDD-ID, invoking other sub-agents in sequence, and ensuring all completion gates are satisfied before advancing. |
| **TDDImplementer**          | Sub-agent that writes failing tests and minimal production code for one TDD item. Operates within the RED-GREEN-REFACTOR cycle under the direction of TDDCycleController.                                                       |
| **RedGreenAuditor**         | Sub-agent that verifies RED (expected failure) and GREEN (expected pass) observations. Ensures the test actually fails before implementation and actually passes after implementation, producing command+result evidence.       |
| **TDDSpecReviewer**         | Sub-agent that reviews spec alignment and detects scope creep. Verifies that the implementation addresses the intended test case and does not introduce functionality beyond the current TDD item's scope.                      |
| **TDDCodeQualityReviewer**  | Sub-agent that reviews code quality beyond style. Evaluates implementation for maintainability, correctness, and adherence to design principles, independent of linting or formatting concerns.                                 |
| **ParallelSliceDispatcher** | Conditional sub-agent that manages parallel execution of independent slices. Only activated when slices meet independence criteria; responsible for worktree separation and post-merge integration verification.                |
| **Completion Contract**     | Formal set of conditions that must all be true before declaring a TDD item or spec complete. Item-level completion requires a 10-point checklist; spec-level completion requires all items resolved and zero blocking issues.   |
| **Evidence Contract**       | Minimum required audit trail per TDD item. Includes TDD-ID, TC-ref, RED command+result, GREEN command+result, refactor verification, and reviewer results. Evidence must be fresh (generated during the current cycle).         |
| **Independent Slice**       | A unit of work with no shared state, no sequential dependency, and no public API overlap with other slices. Only independent slices are eligible for parallel dispatch.                                                         |
| **Fresh Evidence**          | Evidence generated during the current TDD cycle, not reused from previous runs. Ensures that audit trails reflect the actual state of the code at the time of completion.                                                       |
| **Guardrail**               | Automated test that detects the presence or absence of specific phrases in artifacts. Used to enforce that documentation, wrappers, and skill files remain synchronized with the current contract version.                      |
| **Half-migration State**    | A condition where some artifacts (e.g., SKILL.md) reflect a new contract version while others (e.g., wrappers or README.md) still reflect an older version. Detected by wrapper parity checks and forbidden phrase guardrails.  |
| **Wrapper Parity**          | The state where all platform wrappers (.agents/.claude/.codex) contain semantically equivalent descriptions of the same contracts, roles, and rules. Parity drift of zero means all wrappers are synchronized.                  |
