# 01 Context

## 背景

QFAI（Quality-First AI）は、AI コーディングエージェント向けの品質第一開発キット（CLI）である。Node.js 18+ / TypeScript / vitest をベースとし、SDD / ATDD / TDD ワークフローを通じてソフトウェア品質を担保する。

現在 9 つのスキル（qfai-discussion, qfai-sdd, qfai-configure, qfai-prototyping, qfai-atdd, qfai-tdd-red, qfai-tdd-green, qfai-tdd-refactor, qfai-verify）が存在し、各スキルはレビューサイクルを経て成果物の品質を保証する。

レビュー体制として `review-roster.yml` に 10 名のレビュアー（qa-lead, qa-gatekeeper, reviewer, code-reviewer, architect-reviewer, qa-reviewer, frontend-reviewer, backend-reviewer, design-review-lead, runtime-gatekeeper）が定義されている。また `agent-selection.md` には約 20 の委任ロール（Researcher, Orchestrator, Test Volume Estimator 等）が定義されている。

現行のレビュー体制は「建設的フィードバック」を前提としており、根本的な否定や大幅なパターン増強を強制する仕組みが存在しない。その結果、以下の構造的弱点が残っている：

- 成果物の方向性に対する根本的な異議申し立てが行われない（確証バイアスの温床）
- User Story / Acceptance Criteria / Business Rules / Examples / Test Cases 等のパターン数が最低限にとどまりがちで、エッジケースの網羅性が不足する
- レビュアー全員が「改善提案」ベースであるため、全面否定による再考の契機がない

## 目的

本ディスカッションの目的は、QFAI v1.5.6 において以下の 2 つの新規サブエージェントを品質フレームワークに追加することである：

### 1. 全否定エージェント（Devil's Advocate Agent）

- **役割**: 現在の成果物のすべてが間違っているという前提で、自身のビジョンに基づく「あるべき姿」を反論不可能な論理（詭弁・全否定・逆張り）で押し通すレビュアー
- **追加先**:
  - `review-roster.yml` に第 11 番目のレビュアーとして追加
  - `agent-selection.md` に新規委任ロールとして追加
  - 全 9 スキル（qfai-discussion, qfai-sdd, qfai-configure, qfai-prototyping, qfai-atdd, qfai-tdd-red, qfai-tdd-green, qfai-tdd-refactor, qfai-verify）のレビューフェーズで呼び出し
- **ブロッキング権限**: FAIL 判定 = 修正 + レビューロスター全体のフルリスタート

### 2. パターン倍増エージェント（Pattern Doubler Agent）

- **役割**: すべての成果物に対し、パターン数を 2 倍にすることを詭弁・全否定・逆張りで強制するレビュアー
  - SDD 成果物: User Stories, Acceptance Criteria, Business Rules, Examples, Test Cases のパターン倍増
  - その他スキル成果物: 当該スキルに存在するパターン類似成果物の倍増
- **追加先**: 全 9 スキルのレビューフェーズで呼び出し
- **ブロッキング権限**: FAIL 判定 = 修正 + レビューロスター全体のフルリスタート

両エージェントの導入により、確証バイアスの排除とパターン網羅性の大幅向上を同時に実現する。

## ステークホルダー

| ロール                  | 関心事                                                                             |
| ----------------------- | ---------------------------------------------------------------------------------- |
| QFAI ユーザー（開発者） | レビュー品質の向上による成果物の信頼性確保、ただしレビュー時間増加の許容範囲       |
| QFAI エージェント       | 新規サブエージェントの呼び出しタイミングと FAIL 時のフルリスタート挙動の明確化     |
| QFAI メンテナー         | review-roster.yml / agent-selection.md / 全 SKILL.md への変更の整合性と保守性      |
| チームレビュアー        | 既存 10 レビュアーとの役割分担の明確化、レビューサイクルへの影響                   |
| QA リード               | ブロッキング FAIL によるレビュー全体リスタートの品質的意義とコストのバランス       |
| プロダクトオーナー      | パターン倍増によるスペック肥大化と、それに伴う開発工数・LLM トークンコストへの影響 |

## 前提条件

- 対象バージョンは QFAI v1.5.6 である
- 対象スキルは現行の全 9 スキル（qfai-discussion, qfai-sdd, qfai-configure, qfai-prototyping, qfai-atdd, qfai-tdd-red, qfai-tdd-green, qfai-tdd-refactor, qfai-verify）
- 現行 `review-roster.yml` には 10 名のレビュアーが定義されており、第 11 番目として全否定エージェントを追加する
- 現行 `agent-selection.md` には約 20 の委任ロールが定義されており、新規ロールを追加する
- 両エージェントはブロッキング権限を持つ（FAIL = 修正 + レビューロスター全体のフルリスタート）
- 本変更は SKILL.md、review-roster.yml、agent-selection.md 等の設定・仕様ファイルへの変更が中心であり、TypeScript コアロジックの変更は最小限にとどまる見込み
- Node.js 18+ / TypeScript / vitest の既存技術スタックは変更しない
- 全否定エージェントもパターン倍増エージェントも、自身の主張を「絶対に譲らない」設計とする（詭弁・逆張り・全否定を使用）

## 課題

### C-1: レビューサイクルの無限ループリスク

両エージェントが FAIL 判定時にフルリスタートを強制するため、他のレビュアーが PASS した成果物が再度レビュー対象となる。全否定エージェントが常に FAIL を出し続ける場合、レビューサイクルが収束しない可能性がある。

- **検討事項**: 最大リトライ回数の設定、エスカレーションルール、収束条件の定義

### C-2: パターン倍増の実現可能性と品質

パターン数を機械的に 2 倍にすると、意味のない重複パターンや低品質なエッジケースが生成される恐れがある。

- **検討事項**: 倍増の定義（数値目標 vs. 品質基準）、倍増対象の選定基準、既に十分なパターンが存在する場合の扱い

### C-3: LLM トークンコストとレスポンス時間の増大

2 つの新規サブエージェント呼び出し + フルリスタートにより、1 回のスキル実行あたりの LLM トークン消費量とレスポンス時間が大幅に増加する。

- **検討事項**: コスト見積もり、許容範囲の定義、最適化戦略（並列実行、条件付き呼び出し等）

### C-4: 既存レビュアーとの相互作用

全否定エージェントの FAIL によるフルリスタートで、既存 10 レビュアーの PASS 判定が無効化される。既存レビュアーのモチベーション低下（シミュレーション上の）と、レビュー結果の安定性への影響。

- **検討事項**: リスタート時の既存 PASS 結果のキャッシュ戦略、段階的リスタート（全面 vs. 部分）

### C-5: 全スキルへの一貫した組み込み

9 スキルすべてに両エージェントを組み込む必要があるが、スキルごとにレビューフェーズの構造が異なる可能性がある。

- **検討事項**: 共通インターフェースの設計、スキル固有のカスタマイズポイントの定義、SKILL.md テンプレートの標準化
