## Term Definitions

| Term                  | Definition                                                                                                                                                                                                                                       | Context                                   | Source                             |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------- | ---------------------------------- |
| operator              | The person who types the request and answers the run's questions. The decisions D1 to D18 call this person "user".                                                                                                                               | Throughout                                | D1; D5                             |
| harness               | The AI host that runs the agents, shell commands and tests, and submits their results to `npx qfai workflow`: Claude Code or Codex. The CLI never starts it.                                                                                     | Control core; REQ-0014, REQ-0058          | SRC-0001 design 02 AD-01; D2; D3   |
| run                   | One operator request carried through `npx qfai workflow`, from `start` to a terminal state. Its runtime state is in `.qfai/runs/<runId>/`, its durable evidence in `.qfai/evidence/workflow/<runId>/`.                                           | Control core; REQ-0014, REQ-0024          | SRC-0001 design 02 AD-05; D11      |
| stage instance        | One execution of a stage (for example `acceptance`) inside a run. A seam-only round trip returns to the same stage instance.                                                                                                                     | Control core; REQ-0034, REQ-0038          | SRC-0001 design 02 AD-05           |
| attempt               | One try at a stage instance. A retry is a new attempt of the same stage instance, counted against the retry budget.                                                                                                                              | Control core; REQ-0031                    | SRC-0001 design 02 AD-05, 05 §8    |
| work order            | The instruction `next` hands to the stage's author: run, stage instance, attempt, operation, target binding, scope and the author and reviewer history. The smallest unit the core controls.                                                     | Control core; REQ-0016, REQ-0034          | SRC-0001 design 02 AD-05; SRC-0002 |
| request kind          | What the request asks for, decided before any route: `change`, `read_only`, `plan_only`, `verify_only`, `resume`, `cancel` or `explicit_stage`. Only `change` starts a change workflow.                                                          | Intake; REQ-0002                          | SRC-0001 design 03 §1              |
| route                 | The workflow chosen for a `change` request: `direct`, `bugfix`, `bounded-change`, `feature` or `discovery`. Routes are not ranked by size and do not replace the change types `Initial`, `Behavior`, `Structural` and `Ops`.                     | Routing; REQ-0005, REQ-0006               | SRC-0001 design 02 AD-03, 03 §3    |
| route proposal        | The structured routing candidate the agent submits and the core checks: request kind, candidate route, goal, references, affected specs, risk signals, open questions, write scope, required stages and a short rationale.                       | Routing; REQ-0011                         | SRC-0001 design 03 §4; SRC-0002    |
| scope envelope        | What a run may touch: goal, capabilities, specs, contract IDs, allowed effects, non-goals, protected targets and write areas. Reading more never widens it.                                                                                      | Routing and `accept`; REQ-0012            | SRC-0001 design 03 §5              |
| target binding        | The explicit spec a work order acts on, or `new_capability` until SDD creates the spec and binds its ID. Never absent: a missing target is refused, not read as "all capabilities".                                                              | Work orders; REQ-0013                     | SRC-0001 design 05 §2; BP-0002     |
| authorization kind    | One of `request_scope` (what the first explicit request allowed), `human_decision` (a real answer to a specific question) and `project_policy` (a policy the project adopted). Mode, confidence and an agent-written approval are none of these. | Authorization; REQ-0041                   | SRC-0001 design 03 §6              |
| receipt               | The record that a stage's result or a command's outcome was accepted, with its fingerprint and dependencies. Classed `valid`, `stale` or `unknown` on resume.                                                                                    | Acceptance and resume; REQ-0029, REQ-0030 | SRC-0001 design 05 §5, §6          |
| receipt trust level   | How a receipt's result was obtained: `cli_observed` (the CLI ran the command itself), `host_observed` (taken from the host's own record) or `agent_reported` (the agent's statement).                                                            | Final gate; REQ-0060                      | SRC-0001 design 05 §10; D10        |
| completion target     | What `finish` checks a run against: `qfai_done` (every QFAI delivery condition met) or `working_tree` (the change is made and verified in the working tree, delivery conditions not claimed).                                                    | Completion; REQ-0061                      | SRC-0001 design 03 §9              |
| outcome               | A stage result's verdict on the artifact: `accepted`, `accepted_with_debt`, `needs_repair`, `awaiting_input`, `blocked` or `unrun`. Kept separate from the test observation.                                                                     | Stage contracts; REQ-0035                 | SRC-0001 design 04 §5              |
| test observation      | What the tests showed: `pass`, `expected_red`, `fail`, `unrun` or `not_applicable`. A field of a stage result, separate from the skip disposition.                                                                                               | Stage contracts; REQ-0035                 | SRC-0001 design 04 §5              |
| skip disposition      | How the plan records a stage that did not run: `not_applicable` with a reason, or `reused` with a valid receipt. A field of the plan's stage record, not of a stage result; its `not_applicable` is not the test observation of the same name.   | Stage contracts; REQ-0036                 | SRC-0001 design 02 AD-06           |
| accepted_with_debt    | An outcome that hands the stage on while named residual findings remain, each with an owning spec and a resolving owner. A run carrying unresolved debt cannot complete. ATDD's "PASS with cross-spec obligations" is this outcome.              | Stage contracts; REQ-0037                 | SRC-0001 design 04 §6; SRC-0010    |
| expected_red          | A test failing at the assertion it was written to make fail, before implementation. Legitimate input to implement. An import, collection or start-up failure is not `expected_red`.                                                              | ATDD and implement; REQ-0035              | SRC-0001 design 04 §5; SRC-0010    |
| seam-only             | A work order from the acceptance stage asking implement for only the minimal route, export or module an acceptance test needs to reach its assertion, after which control returns to the same acceptance stage instance.                         | ATDD round trip; REQ-0038                 | SRC-0010; SRC-0001 design 04 §4    |
| diagnose-only         | An operation of `/qfai-implement` that reproduces and explains a defect without changing product code, and returns one of four verdicts: missing test, defective test, regression caught by an existing correct test, or differing expectation.  | Bugfix route; REQ-0045                    | SRC-0001 design 04 §3; D6          |
| orchestrated mode     | A stage skill running because `qfai-run` handed it a valid work order. It validates the binding instead of asking again and ends where the work order ends.                                                                                      | Skills; REQ-0051, REQ-0052                | SRC-0001 design 06 §2; D12; D15    |
| standalone mode       | A stage skill invoked by name by the operator. It runs that stage alone and ends there, as today.                                                                                                                                                | Skills; REQ-0053                          | SRC-0001 design 06 §2              |
| active / shadow / off | The workflow mode in `qfai.config.yaml`. `active` (default) chains stages automatically; `shadow` proposes a route and its reason and writes nothing; `off` is manual operation as today.                                                        | Configuration; REQ-0059                   | SRC-0001 design 07 §5; D7          |
| fail-closed           | Leaving automatic chaining when a runtime invariant is violated, a required host capability is missing or policy has drifted (the three drift triggers are in REQ-0059), instead of continuing with less checking.                               | Mode; REQ-0059                            | SRC-0001 design 07 §5; D7          |
| fault seed            | One of 24 scripted runtime failures (an interrupted write, a stale approval, a resubmitted result, a shared report and others) run as a deterministic test.                                                                                      | Evaluation; REQ-0066                      | SRC-0002 runtime-fault-cases.json  |
| routing seed          | One of 64 request-and-repository cases used to evaluate routing with a real model. Synthetic until wired to fixtures.                                                                                                                            | Evaluation; REQ-0066                      | SRC-0002 router-seed-cases.jsonl   |

## Abbreviations

| Abbreviation | Full Form                            | Notes                                                                                                     |
| ------------ | ------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| CAS          | compare-and-set                      | An event is written only if the run's sequence and previous-event hash are what the writer expected.      |
| CR           | Change Request                       | The existing document that asks an upstream owner for a change. Not used for a spec-unchanged bugfix row. |
| TC           | test case                            | A row in a spec's `06_Test-Cases.md`.                                                                     |
| AC / BR      | acceptance criterion / business rule | In a spec pack. A test-defect fix must leave the cited AC or BR unchanged.                                |
| RED / GREEN  | failing / passing test state         | The TDD cycle states recorded in the execution ledger.                                                    |

## Rules

- Terms must be used consistently across all discussion artifacts.
- Ambiguous or context-dependent terms should include usage context.
