# 06 Test Cases

## Purpose

- Verify the examples and the acceptance criteria with explicit references.
- Each AC has a `normal` case, a case for every valid boundary it declares, and one error
  case for every kept failure it names. No failure is added that CLI-WF, CLI-WFFILE or a rule
  of this spec does not declare.
- Every code, reason and cause a case names is one CLI-WF or CLI-WFFILE names. A case holds
  the literal value it asserts, and no test parses a contract.
- A matrix-shaped case names each of its boundaries in `Steps`. Phase 2b gives each boundary
  its own ledger row.

## Level vocabulary

Each row's `Level` follows
`.qfai/assistant/catalog/test-layers.md#layer-derivation-procedure-normative`. The oracle
decides the level, and the decision function named in `01_Spec.md` `## Design` is the
interface an L1 case observes.

- `L1` — the verdict and the events `decide(snapshot, input, facts)` returns for inputs
  the test supplies. The tests live in `packages/qfai/tests/unit/workflow/`.
- `L2` — the mapping of `EBUSY`, `EPERM` and `EACCES` to `io-error` through a write function
  the test injects. It shares `packages/qfai/tests/unit/workflow/`.
- `L3` — real files, git, the lock, the ledger read with the existing parser, validate run
  in process, the built CLI's stdout and exit code, or a scan of the repository's tracked
  files. Every L3 case lives in `packages/qfai/tests/integration/workflow/`, the workflow CLI
  cases included.

No row is L4 or L5. The CLI contracts are not `CON-API-*`, and a journey is a `US-*`
obligation (`## E2E journeys` below). The same L1, L2 and L3 cases run on the Linux and the
Windows jobs. Four cases exist only because their setup differs by platform, and their
`Notes` say so.

`Type` is `normal`, `error`, `boundary` or `edge`. `edge` covers replays, crash states, lock
takeover, glob membership and path aliases.
