# 05 Examples

## Purpose

- Concretize BR into executable examples.
- Every EX must reference at least one BR via `BR-Ref`.
- One EX per BR, index-aligned: the example whose trailing number is _n_ concretizes the business
  rule whose trailing number is _n_, for every rule in `04_Business-Rules.md`. The 1:1 mapping is
  deliberate: `04_Business-Rules.md` § `Granularity (required)` already folds a rule's
  planted-violation form into the same BR as its positive assertion, so a second EX per rule would
  split an oracle that the rule keeps together.
- `Input` is what a test sets up or reads; `Expected` is the observable that falsifies the rule
  when it disagrees. Where the rule is a **sequencing** or **record-keeping** obligation, the
  observable is a repository artifact (`07_Decisions.md`, the merge order, the evidence quoted in a
  pull-request description) rather than a program output — those rules are violable by merge order
  or by omission, not by a file's contents.

## Scope reminder

Every example below reads or plants against **QFAI's own** toolchain — `.github/workflows/**`,
`.github/actions/**`, root `scripts/**`, `packages/qfai/scripts/**` and the test-runner
configuration. Where an example names the shipped tree
(`packages/qfai/assets/init/root/.github/workflows/**`) it is an input to the **lane that scans
it**; the files themselves are `spec-0003`'s, per
`.qfai/contracts/cli/shipped-workflows.md` §1 / §3. No example here asserts what a shipped file
must contain except through the hygiene lane's shipped-file rules (`CLI-WFSET` §6).
