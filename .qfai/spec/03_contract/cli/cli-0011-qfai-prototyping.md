# CLI-0011: Prototyping

## Ownership boundary

This contract decides the prototyping loop behind `/qfai-prototyping`: which UI
contracts a session covers, how a review is scored, that prototyping completes
on the user's confirmation, where the loop keeps its files, and the handoff
record it leaves for implementation.

How a prototype stage runs inside a route is decided by the `qfai workflow`
contract (CLI-0015).

## Business rules

No `qfai` command writes them, and `qfai validate` checks no prototype. The primary contract selects the initial prototype context; every UI-bearing contract and its declared screens are still reviewed, unless the run is scoped to part of a prototype the user already confirmed. | EX-0001-0138-01 |
| BR-0011-0006 | A `prototyping.primaryUiContract` value the config loader rejects, such as the retired `CON-UI-NNNN` form, never lets another UI contract become primary. A standalone invocation still resolves every UI-bearing contract. | EX-0001-0204-03 |
| BR-0011-0008 | When no UI-bearing contract serves the flow a route's prototype stage is for, `/qfai-prototyping` writes nothing — no `DESIGN.md`, no UI contract and no surface declaration — and the session stops, naming the missing UI surface and the flow. | EX-0001-0204-04 |

| BR-0011-0016 | The shipped reviewer prompt uses the four fixed ordinal UX axes in the per-cycle summary: information architecture, navigation flow, usability, and functionality. | BR-0011-0017 | The shipped reviewer prompt includes a concrete actionable critique and a contrasting overly lenient critique. No calibration sidecar is emitted. | EX-0001-0084-01 |
| BR-0011-0018 | The reviewer writes `pivotDirective` by the rule the shipped reviewer prompt states. Menu reachability is part of `navigationFlow`, not a fifth axis. | EX-0001-0116-04 |
| BR-0011-0027 | Before scoring, the reviewer receives the live prototype (in a `restyle` iteration, the live routes the iteration lists, which it opens in the running app), root `DESIGN.md`, prior review context, the layout anti-pattern catalog and, in a `restyle` iteration, each route's baseline. | BR-0011-0029 | The session agent generates, and `product-surface-reviewer` scores each review from a fresh context and a black-box brief. An assignment that gives review scoring to the session agent, or generation to the reviewer, is reported before either runs. | EX-0001-0097-02 |
| BR-0011-0030 | `prototyping.execution.browserTool` accepts `playwright`, and any other value is a configuration error. The shipped `qfai.config.yaml` sets `playwright` as the default. | EX-0001-0129-01 |
| BR-0011-0031 | When the user confirms the prototype, the `/qfai-prototyping` handoff step copies the accepted iteration to `.qfai/prototype/final/index.html`, or in a scoped run merges its in-scope parts into it, and writes `.qfai/prototype/final/handoff.json`, a record of the canonical handoff schema (CLI-HANDOFF) whose per-skill extension fields are `finalArtifact` (the repository-relative path of the final prototype), `procurement` (the `procured`, `authored` and `drawn-from-project` lists of what realises each screen region) and `implementationNotes` (prose). | BR-0011-0042 | The shipped `/qfai-prototyping` skill speaks of one UI contract (`UI-NNNN`) as its unit and names no internal scope-resolution helper. A documentation check holds the shipped skill to no multi-spec wording. | EX-0001-0134-01 |
| BR-0011-0100 | Prototyping completes when the user confirms the prototype, or stops before iteration 00 when a `restyle` audit at `none` had no refinement accepted. Until then the loop runs another iteration on the user's answer, and no command, score or check certifies completion; a blocking finding still open when the user confirms is named in the final report. | EX-0001-0228-01, EX-0001-0228-02, EX-0001-0228-03, EX-0001-0295-06 |
| BR-0011-0101 | The loop records `iterationKind` in `.qfai/prototype/progress.md`: `prototype`, the default, or `restyle` when the request changes only the styles and motion of screens the project already runs, keeping their screens, fields and behaviour. A `restyle` iteration restyles the live app in place: the generator edits the project's stylesheet and motion entry points, the iteration's `index.html` lists the live routes in scope with one link per declared screen, each with its absolute URL and the setup it needs, and the reviewer opens each listed route in the running app. Preflight also checks that the live app's URL answers. The restyle's edits are product code that the route's implement stage carries, where they are change-noted, gated, tested and committed, so a restyle needs a scope that includes the implement stage. A request extracted with the qualifier `restyle` is planned with only such scopes, and a loop whose route scope has no implement stage stops before iteration 00 and asks the user to re-plan. The kind comes from the request, and the live app is already running at preflight. | EX-0001-0228-05, EX-0001-0228-06 |
| BR-0011-0102 | A `/qfai-prototyping` run may be scoped to part of a prototype the user already confirmed. The optional `## Run scope` section of `.qfai/prototype/grilling.md`, written afresh each run, names screens as `<ui-contract-id>/<screen>` and shared components by repository path or by their `procurement` item; with no or an empty run scope, without an earlier `.qfai/prototype/final/index.html` and a `final/handoff.json` carrying both `finalArtifact` and `procurement`, or in a `restyle` loop, the run covers the whole product, and a declared screen outside the scope that lacks a route in `final/index.html` or a `procurement` row joins the scope. Each run records `runScope` in `progress.md` afresh before its first iteration, overwriting any earlier one: the in-scope screens, the in-scope components, and each render-check screen with the component it renders, or absent when the run is not scoped. The run's first iteration is the first after that record, and no earlier run's review, score or confirmation is its prior review or the user's last answer. A scoped run's first iteration starts from a copy of `final/index.html`, each later one builds on the previous iteration, only the in-scope screen routes and components change, and a `pivot` applies only inside the scope. The reviewer reviews the in-scope screens in full and, on each other screen that renders an in-scope component, only that the component renders, and opens no other screen. The handoff replaces in `final/index.html` only the in-scope screen routes and each place a route renders an in-scope component, keeps every other part and every other `procurement` row, and records the confirmed scope as `runScope` in `final/handoff.json`, keeping its other keys; the confirmed prototype is the whole of `final/`. | EX-0001-0228-07, EX-0001-0228-08 |
