# CLI-0011: Prototyping

## Ownership boundary

This contract decides the prototyping loop behind `/qfai-prototyping`: which UI
contracts a session covers, how a review is scored, that prototyping completes
on the user's confirmation, where the loop keeps its files, and the handoff
record it leaves for implementation.

How a prototype stage runs inside a route is decided by the `qfai workflow`
contract (CLI-0015).

## Business rules

| BR-ID | Statement | Examples |
| --- | --- | --- |
| BR-0011-0001 | `/qfai-prototyping` keeps its working files, the prototype, its reviews and the handoff, under `.qfai/prototype/`; a `restyle` loop also edits the project's stylesheet and motion entry points its handoff names, and no other file outside that folder. No `qfai` command writes them, and `qfai validate` checks no prototype. The one file a command reads there is the handoff record `.qfai/prototype/final/handoff.json`, which `qfai validate --profile saas-package` checks against the CLI-HANDOFF schema. | EX-0001-0228-04, EX-0001-0228-06 |
| BR-0011-0002 | `/qfai-prototyping` is the interface to prototyping: the skill runs the build and review loop with the user, and the `qfai` command has no `prototyping` command group. | EX-0001-0228-01 |
| BR-0011-0003 | One `/qfai-prototyping` invocation resolves every UI-bearing UI contract under `<paths.contractsDir>/ui/`: a YAML file that declares one full `UI-NNNN` ID and a non-empty `screens[]`. The invocation does not prompt for a primary contract and reads no spec-level marker. With no UI-bearing contract it writes nothing and says that none was resolved. | EX-0001-0114-02, EX-0001-0114-03 |
| BR-0011-0004 | Only a UI contract declaring a `UI-NNNN` ID and a `screens[]` entry is UI-bearing. No spec-level marker is read, and the current scope is never inferred from spec packs or marker titles. | EX-0001-0114-01 |
| BR-0011-0005 | The primary UI contract is pinned by `prototyping.primaryUiContract` in `qfai.config.yaml` or named in the request, and the request takes precedence. Both accept only the full `UI-NNNN` form: any other value is refused, naming the `UI-NNNN` shape and the value received, and no value is normalised. The primary contract selects the initial prototype context; every UI-bearing contract and its declared screens are still reviewed, unless the run is scoped to part of a prototype the user already confirmed. | EX-0001-0138-01 |
| BR-0011-0006 | A `prototyping.primaryUiContract` value the config loader rejects, such as the retired `CON-UI-NNNN` form, never lets another UI contract become primary. With no primary contract named in the request, `/qfai-prototyping` stops before it writes anything, naming the key and the value received. | EX-0001-0138-02 |
| BR-0011-0007 | In a route for a business flow, `/qfai-prototyping` works only on the UI-bearing contracts that serve that flow; a contract serves a flow when one of its rules cites an example of one of that flow's stories. It settles the one visual decision the plan needs within the existing root `DESIGN.md` and those contracts, changes no UI contract that serves only another flow, and creates no contract. A standalone invocation still resolves every UI-bearing contract. | EX-0001-0204-03 |
| BR-0011-0008 | When no UI-bearing contract serves the flow a route's prototype stage is for, `/qfai-prototyping` writes nothing — no `DESIGN.md`, no UI contract and no surface declaration — and the session stops, naming the missing UI surface and the flow. | EX-0001-0204-04 |
| BR-0011-0015 | Each UX axis score is one of `weak`, `acceptable`, `strong` or `exceptional`, and any other value is rejected. The scale carries no ordinal index. | EX-0001-0105-01 |
| BR-0011-0016 | The shipped reviewer prompt uses the four fixed ordinal UX axes in the per-cycle summary: information architecture, navigation flow, usability, and functionality. It follows the closed per-screen review payload schema for six bounded impressions and blocking findings, and the screen payload carries no axis rating; no weighted visual score or AC-pass percentage decides convergence; no discussion-pack rubric defines these fields. | EX-0001-0083-01, EX-0001-0107-01 |
| BR-0011-0017 | The shipped reviewer prompt includes a concrete actionable critique and a contrasting overly lenient critique. The actionable case identifies the screen, observed defect, correction, and blocking finding; a favorable score or vague praise cannot replace that finding. No calibration sidecar is emitted. | EX-0001-0084-01 |
| BR-0011-0018 | The reviewer writes `pivotDirective` by the rule the shipped reviewer prompt states. With `open(r)` the number of `blockingFindings` plus `layoutAntiPatternsDetected` in review `r`, it is `pivot` when `open(latest) > 0`, `open(latest) >= open(prior)` and `open(prior) >= open(prior2)`; otherwise `continue` when a prior review exists and `open(latest) < open(prior)`; otherwise `refine`. | EX-0001-0105-02, EX-0001-0105-03, EX-0001-0105-04 |
| BR-0011-0019 | `layoutAntiPatternsDetected[]` holds only identifiers the layout anti-pattern registry the package ships declares, and a detection caps `informationArchitecture` at `acceptable`. | EX-0001-0108-01, EX-0001-0108-02 |
| BR-0011-0020 | Menu reachability is qualitative. The reviewer exercises every primary menu entry the UI contract declares at least once in its Playwright session, and records what it found in `menuReachabilityFeel`; an unreachable entry is critique only and does not fail the cycle. Menu reachability is part of `navigationFlow`, not a fifth axis. | EX-0001-0116-04 |
| BR-0011-0027 | Before scoring, the reviewer receives the live prototype (in a `restyle` iteration, the live routes the iteration lists, which it opens in the running app), root `DESIGN.md`, prior review context, and the layout anti-pattern catalog. Screenshots and HTML snapshots are additional inputs only when the loop captured them. A finding names any missing mandatory input. The reviewer checks the prototype against every category root `DESIGN.md` declares and names each mismatch in a finding or in `designMdViolations[]`. | EX-0001-0102-01, EX-0001-0103-01, EX-0001-0228-05 |
| BR-0011-0028 | The delegation map names owners for implementation, review scoring, and build, and has no fixed capture identity. An invalid assignment is reported at planning, before any role is dispatched. Execution planning records `targetIterations`, `evaluationAxesSource`, `delegationMap` and `plannedAt` before the first review. | EX-0001-0097-01, EX-0001-0099-02, EX-0001-0099-01 |
| BR-0011-0029 | At dispatch, generation and review use distinct sub-agent identities, and an assignment that reuses one identity for both is reported before either runs. | EX-0001-0097-02 |
| BR-0011-0030 | `prototyping.execution.browserTool` accepts `playwright`, and any other value is a configuration error. The shipped `qfai.config.yaml` sets `playwright` as the default. | EX-0001-0129-01 |
| BR-0011-0031 | When the user confirms the prototype, the `/qfai-prototyping` handoff step copies the accepted iteration to `.qfai/prototype/final/index.html`, or in a scoped run merges its in-scope parts into it, and writes `.qfai/prototype/final/handoff.json`, a record of the canonical handoff schema (CLI-HANDOFF) whose per-skill extension fields are `finalArtifact` (the repository-relative path of the final prototype), `procurement` (the `procured`, `authored` and `drawn-from-project` lists of what realises each screen region) and `implementationNotes` (prose). In a `restyle` loop the step copies nothing, and the record's extension fields are instead `iterationKind` (`restyle`), `liveRoutes` (the live routes the confirmed iteration listed, at least one), `entryPoints` (the `stylesheet` and `motion` lists of the files the restyle changed) and `implementationNotes`; `npx qfai validate --profile saas-package` reports a `restyle` record without a non-empty `liveRoutes` or without both `entryPoints` lists. `/qfai-implement` reads it as a CLI-HANDOFF record. | EX-0001-0228-01, EX-0001-0095-01, EX-0001-0228-05, EX-0001-0095-02 |
| BR-0011-0042 | The shipped `/qfai-prototyping` skill speaks of one UI contract (`UI-NNNN`) as its unit and names no internal scope-resolution helper. A documentation check holds the shipped skill to no multi-spec wording. | EX-0001-0134-01 |
| BR-0011-0100 | Prototyping completes when the user confirms the prototype. Until then the loop runs another iteration on the user's answer, and no command, score or check certifies completion; a blocking finding still open when the user confirms is named in the final report. | EX-0001-0228-01, EX-0001-0228-02, EX-0001-0228-03 |
| BR-0011-0101 | The loop records `iterationKind` in `.qfai/prototype/progress.md`: `prototype`, the default, or `restyle` when the request changes only the styles and motion of screens the project already runs, keeping their screens, fields and behaviour. A `restyle` iteration restyles the live app in place: the generator edits the project's stylesheet and motion entry points, the iteration's `index.html` lists the live routes in scope with one link per declared screen, each with its absolute URL and the setup it needs, and the reviewer opens each listed route in the running app. Preflight also checks that the live app's URL answers. The restyle's edits are product code that the route's implement stage carries, where they are change-noted, gated, tested and committed, so a restyle needs a scope that includes the implement stage, today only `broad`, and a loop whose route scope has none stops before iteration 00 and asks the user to re-plan. The kind comes from the request, and the live app is already running at preflight. | EX-0001-0228-05, EX-0001-0228-06 |
| BR-0011-0102 | A `/qfai-prototyping` run may be scoped to part of a prototype the user already confirmed. The optional `## Run scope` section of `.qfai/prototype/grilling.md`, written afresh each run, names screens as `<ui-contract-id>/<screen>` and shared components by repository path or by their `procurement` item; with no run scope, with no earlier `.qfai/prototype/final/index.html`, or in a `restyle` loop, the run covers the whole product. A scoped run's generator starts each iteration from a copy of `final/index.html` and changes only the in-scope screen routes and components. The reviewer reviews the in-scope screens in full and, on each other screen that renders an in-scope component, only that the component renders, and opens no other screen. The handoff replaces in `final/index.html` only the in-scope screen routes and each place a route renders an in-scope component, keeps every other part and every other `procurement` row, and records the confirmed scope as `runScope` in `final/handoff.json`; the confirmed prototype is the whole of `final/`. | EX-0001-0228-07, EX-0001-0228-08 |
