# CLI-0001: Assistant Routing

## Ownership boundary

This contract decides how QFAI's assistant work is delegated and reviewed: the
agent cards as the only agent definition, the two reasons the session
delegates and the hard stop when a delegation fails, reviewer independence,
the Default Autopilot Policy of every skill, the handoff schema shared across
skills, and the Reviewer Gate findings that guard those surfaces.

`cli-0002-assistant-steps.md` decides the step tree, and
`cli-0004-delivery-workflow.md` the parallel-unit gate.
`cli-0014-qfai-validate.md` decides the machine findings for a missing or
misdeclared card, `cli-0009-qfai-init.md` decides the shipped
assistant tree and its host links, and `cli-0015-qfai-workflow.md` decides the
reviews a route holds and the decisions it puts to the user.

| BR-0001-0002 | Delegation by Context - The session agent authors every artifact itself: research, design, the specification, code, tests and documentation. - It starts a sub-agent for exactly two reasons: an independent judgement of work it produced, which is a review, the finder, a griller or the prototyping evaluator; and two or more parallel units that pass the parallel-unit gate `cli-0004-delivery-workflow.md` states. - Context size, a technical domain and keeping its own context small are not reasons; the host's compaction handles a long run. - The host's built-in agents follow the same two reasons. An agent that only stands in for a tool the host lacks, and returns that tool's result, counts as a tool call. - No sub-agent inherits the session's conversation: each starts from a self-contained brief. On Codex the shared delegation baseline sends the session to the Codex delegation notes before it delegates: `fork_turns: "none"`, one final answer and no interim messages, a wait of minutes, and no polling. - A judgement brief holds the fixed revision, which is a commit, or the base commit with the exact diff of the uncommitted work saved where the judge can read it; the request in the user's own words; the story tree and contracts that bind the work; the written decisions; and the remit. It never holds the author's rationale or self-assessment. A host that can only fork the conversation is `unavailable` for a judgement. - The finder runs on `requirements-reviewer`. A griller runs on `requirements-reviewer`, or on `architecture-reviewer` where the decision is a contract or architecture decision. - The session never judges its own work. | EX-0001-0224-02, EX-0001-0224-53, EX-0001-0163-08, EX-0001-0163-09, EX-0001-0163-10, EX-0001-0163-11, EX-0001-0163-12 |
| BR-0001-0003 | Capability Probe By Real Delegation - No delegation attempt is required at the start of a stage; the session delegates only when it chooses to. - When it does, the real delegation attempt is the capability check; no preflight availability confirmation gates execution. | EX-0001-0163-02 |
| BR-0001-0004 | Delegation Failure Report - Delegation is optional. When a delegation the session chose to make fails, classify it before responding. Classify `saturated` only when the identical call would succeed later with no change by anyone; a limit or quota only a user can lift, and any reason whose retryability is not explicit, is `unavailable`. - If the class is `saturated`, retry the identical delegation with bounded backoff; on exhausting the retry budget, handle it as `unavailable` and report the class as `saturated (retry budget exhausted)`. - If the class is `unavailable`, the session does the work itself, except an independent judgement (a review, the finder, a griller or the prototyping evaluator): there the stage stops. - Do not simulate an agent: work the session did itself is reported as its own. - Report: attempted agent, attempted task, failure summary, failure class, and whether the session did the work or the stage stopped; a stop adds the required user remediation and the retry condition. | EX-0001-0163-01, EX-0001-0163-06 |
| BR-0001-0008 | All-Reviewer Fix Obligation - Every reviewer returning `REVISE` MUST give each blocking finding a concrete fix. - Feedback without a concrete fix is invalid. | EX-0001-0166-01 |
| BR-0001-0011 | Default Autopilot Policy 3-bucket contract - Per DR-0269, every `qfai-*` skill works under the three buckets the operating baseline's `## Default Autopilot Policy (Shared)` states; a skill's own `## Default Autopilot Policy` lists only what it adds: - **auto-decide** (named defaults, AI proceeds without prompting): output formatting, ID / sequence numbering, append-vs-create when a subject overlaps an existing artifact, and option-pick among demonstrably-equivalent alternatives. - **ask-user** (AI prompts via `AskUserQuestion` with the bucket's prompt template): approval-required governance operations, destructive operations, version-pin changes, scope expansions. The first entry is a **category**: each skill instantiates it with the operations its own run cannot authorize for itself — the triage ops (CREATE / DELETE / SPLIT / MERGE / SUPERSEDE / UPDATE:REMOVE) in `/qfai-sdd`, and the Drift-Protocol Change-Request escalation in `/qfai-implement`. A skill's instantiation must cover every decision its own body already gates on a user. Parallel dispatch is not one: the session agent decides it under the parallel-unit gate. Per DR-0269 Amendment 4 the bucket carries a fifth category — **a decision a declared grilling session puts to the user** — available only to a skill whose own operation is the interview (`/qfai-grilling`, `/qfai-grill`), which is what makes their frontier decisions and closing confirmation a legal entry rather than a widening. - **hard-required** (no default possible; must be supplied before proceeding): brand intent, and the inputs declared for the skill. - What the three buckets classify is the **operations the skill performs** — what it may do without asking, what it asks before doing, and what it may not do at all without a value. A **frontier decision** put inside a grilling session is not one of those: it settles a design, an approach, a scope boundary or a trade-off before anything is performed, and `.agents/rules/grilling.md` owns which of those are asked and in what order. Reading the buckets as a classification of every question an invocation can utter is what made the closed `ask-user` list contradict that rule. Two things are outside the carve-out and stay classified by their subject wherever they are asked: a mandatory approval, and a `hard-required` input the invocation consumes. Running inside a session changes neither — a `hard-required` input asked there still stops a run that cannot get it, rather than being guessed. - A prototype entry a skill never reaches costs nothing, so no skill restates the prototype to drop one. A skill MAY instantiate a category entry with its own operations, but MUST NOT add an entry outside the prototype's categories; such an auto-decide entry is reported as `QFAI-POLICY-002` at warning. - Reviewer Gate emits `QFAI-POLICY-001` (severity error, non-empty `justification:`) against the baseline when its shared section is absent or lacks any one of the three buckets, naming every missing bucket, and against a skill whose own section does not name a hard-required input declared for it, naming that input. | EX-0001-0169-01, EX-0001-0169-04 |
| BR-0001-0013 | Cross-skill handoff schema SSOT-sync Pair IV - The package holds one canonical handoff schema (CLI-HANDOFF), documented in `references/handoff.md`. A handoff record keeps the task state and the next action. Minimum field set: `companyName?` / `primaryUiContract?` / `startDate?` / `signature?` / `entryPattern?` / `productScope?`; `additionalProperties: true` so per-skill extensions do not break existing writers. - Every skill that produces / consumes handoff state MUST read / write this schema (the schema and all skill writers form SSOT-sync Pair IV). - No other handoff file is read: a per-skill file such as `session-handoff.yaml` is ignored. - Reviewer Gate emits `QFAI-HANDOFF-001` (severity error, non-empty `justification:`) when the schema ↔ writer pair is edited asymmetrically. A prototyping record that does not conform is reported by `QFAI-SAAS-002` in the `saas-package` profile. | EX-0001-0171-01 |
| BR-0001-0017 | The Card Frontmatter Is the Only Agent Definition - The catalogue the package ships under `.qfai/assistant/agent/` holds five cards: `fullstack-engineer`, the one card of `kind: worker`, and the reviewers `requirements-reviewer`, `architecture-reviewer`, `implementation-reviewer` and `product-surface-reviewer`, each of `kind: reviewer`. No card is defined by a technical domain. - Every agent the shipped skills, steps, rules and cards name is a card of that catalogue; the package's own asset checks hold it to both, and `qfai validate` does not, so a card an earlier release left in a project raises no finding. - An agent's card is its only definition. - The card's frontmatter carries `kind`, `domain`, `mission`, `replaces`, `owned_artifacts`, `tool_profile`, `permission_profile` and `specialization_tags`. Its `name` is the agent's ID. - `mission` is a key of its own. `description` stays the host's one-line summary and is not read as the mission. - Every reader of those fields, including the runtime readers of `kind`, reads them from the card frontmatter. - The host integration files, the generated Codex agent TOML among them, are generated from the card and never authored by hand. - No `agent-catalog.yml` is written or read, so no catalog entry carries a `developer_instructions` copy of a card body. - The card body has substantive Mission, Inputs you must read, Deliverables, Stop conditions, and Sign-off sections. - The assistant tree is stated in `cli-0009-qfai-init.md`. | EX-0001-0161-01, EX-0001-0161-10, EX-0001-0161-11, EX-0001-0162-01 |
| BR-0001-0021 | Stage-Skill Descriptions State When to Use Them - The `description:` of every skill that owns a step a built-in plan names opens with its trigger condition: use it when it is invoked by name or handed a QFAI work order. - Nothing precedes that condition, and the description does not walk through the skill's steps. - It stays within 1024 characters and holds no `<` or `>`. - The skill set is read from the owners of the steps the stage-kind vocabulary of `cli-0020-workflow-files.md` lists; no rule types it as a list. - The shipped skill inventory is the skill tree of the installed package, and the step inventory its step tree. No rule fixes a count of either or names a retired skill as part of them. | EX-0001-0195-07 |
| BR-0001-0022 | No Stage Skill Blocks Model Invocation - No skill that owns a step a built-in plan names carries `disable-model-invocation` in its `SKILL.md` frontmatter, so `qfai-run` can call every stage. - A skill that owns no such step is outside this rule. | EX-0001-0195-09 |
| BR-0001-0025 | Routes Are Not Change Types - The shipped `workflow.md` states that the workflow routes are orthogonal to the Change Type values: a route neither selects nor declares a Change Type, and a Change Type selects no route. | EX-0001-0004-07 |
| BR-0001-0030 | Reviewer Independence - An agent that authored or recommended an artifact never counts as that artifact's independent reviewer. - No required reviewer is dropped to save tokens; an unavailable delegation for a required review stops the work, as the delegation hard stop states. - The shared delegation baseline states this rule. | EX-0001-0163-04 |
| BR-0001-0032 | A Bugfix That Changes No Story-Tree File Raises No Change Request - `drift-protocol.md` keeps every exception it lists, and states that a bugfix whose diff changes no file under `01_policy/`, `02_business-flow/` or `paths.contractsDir` appends no `Change request:` row. - A `Change request:` row naming a story file the bugfix did not touch states an upstream change that did not happen. | EX-0001-0002-07 |
| BR-0001-0033 | A Hard-Required Entry Is Read as a Whole Name - `QFAI-AUTOPILOT-001` is raised at error for a `qfai-*` skill whose `hard-required` bucket names an entry the skill may not carry. - A skill may carry brand intent and the inputs declared for that skill, and nothing else. A declared input its bucket does not name raises `QFAI-POLICY-001` at error instead. - An entry matches only as a whole name: a letter, a digit or a `-` directly before or after it makes it part of a longer name. So a bullet naming the retired `CON-UI-NNNN` does not name the `UI-NNNN` that `qfai-verify` declares, and is reported. | EX-0001-0169-05 |
| BR-0001-0034 | The Triage Stage Skill - `qfai-triage` is a stage skill that owns the nine `triage-*` steps, so the description and invocation rules for stage skills cover it. - Invoked by name it runs the steps its body selects for the request, changes no tracked project file, and ends at its stage. | EX-0001-0214-05, EX-0001-0214-06 |
| BR-0001-0036 | A Stage-Skill Description Names Its Own Subject - After its trigger condition, the `description:` of every skill that owns a step a built-in plan names states the skill's subject. - No two of those descriptions state the same subject, so a request fits one stage and the host can tell adjacent stages apart. | EX-0001-0195-12 |
| BR-0001-0037 | The Entry Skill's Description Names the Free-Text Request - The `description:` of `qfai-run` says to use it when the user asks for a change, a fix, an investigation of the codebase, a question about the project or an operation on finished work in plain words and names no stage skill, and names no request the skill does not plan. - The free-text entry reminder sends each such request that names no skill, the lightest included, to `qfai-run`, and leaves the list of requests to its description. | EX-0001-0196-43, EX-0001-0196-44 |
| BR-0001-0038 | A Selectable Skill Description Says When to Select It - The `description:` of every shipped skill that does not declare `disable-model-invocation: true` carries a sentence beginning `Use when`, is written in the third person, and stays within 1024 characters. - The skill's `name` holds neither `anthropic` nor `claude`. - A skill that declares `disable-model-invocation: true` is started by name, so the rule does not cover it. | EX-0001-0195-13 |
