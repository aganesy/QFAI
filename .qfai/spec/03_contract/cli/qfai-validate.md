# CLI Contract: `qfai validate`

- Contract scope: public CLI surface for spec / contract / assistant-tree validation, and the flow scope `qfai report` shares with it (`### Flow scope`)
- Owning flow: `BF-0001`
- Used-by: post-init self-checks, `qfai report --flow`, and skill completion gates
- SSOT modules:
  - `packages/qfai/src/cli/commands/validate.ts`
  - `packages/qfai/src/cli/commands/report.ts` (the flow-scoped report input and
    output)
  - `packages/qfai/src/core/paths/assistantPaths.ts` (canonical relative paths SSOT)
  - `packages/qfai/src/core/validators/reviewerGate.ts` (Reviewer-Gate inputs)
  - `packages/qfai/src/core/validators/reviewerJustification.ts`
    (Reviewer-Gate `R-*` justification outputs)

## Existing public surface

`qfai validate` reads the story tree under `paths.specsDir` and the contracts
under `paths.contractsDir`. The stage profiles are `discussion`, `sdd`,
`prototyping`, `atdd`, `tdd`, `drift`, `full`, `verify` and `saas-package`.

## Reviewer-Gate input bundle

Reviewer subagents (`completion-reviewer`, `implementation-reviewer`, `qa-gatekeeper`) MUST be invoked with a structured input bundle containing:

1. The Decisions table in `decisions.md`
2. The fresh implementation output under review

A Reviewer finding requires a justification when its code is `R-REJECTED-READOPT`, another code this contract declares with a required `justification:`, or a code the justification catalog registers. Such a finding MUST carry a `justification:` field with non-empty content naming:

- (a) the Decisions row ID that triggered the finding, and
- (b) the specific contradiction or re-adoption observed.

`qfai validate` rejects Reviewer reports in which such a finding lacks `justification:` content. A finding in any other code raises no justification error, and neither does a code whose catalog registration `shipped-workflows.md` defers. This is the machine-checkable acceptance criterion that makes drift-checks advisory-failing rather than mute.

## Layout cutover

`qfai validate` reads the story tree. A spec-pack directory under the configured `paths.specsDir` or the former default `.qfai/specs/` raises one `QFAI-LAYOUT-001` error and stops profile validation. The finding names `/qfai-migration-spec-to-story`.

Repository hygiene accepts `.qfai/spec/` as the canonical story-tree root.
`QFAI-HYG-001` applies to former directory aliases such as `.qfai/specs/`
and `.qfai/specification/`; its repair points to `.qfai/spec/`. A directory
explicitly selected by `paths.specsDir` is not a hygiene alias. When a former
root contains a spec pack, `QFAI-LAYOUT-001` stops validation before hygiene
runs, so the command reports one migration finding.

The former spec-pack and TC coverage readers are retired from the validate
profiles. Their `QFAI-SPACK-103`, `QFAI-ATDD-134` and `QFAI-ATDD-135`
diagnostics are not emitted by the story-tree profiles. A story-tree test scan
that fails or reaches its file cap emits `QFAI-SCAN-002` as an error and does
not report missing BF, AC or EX coverage from a partial scan.

## Profile-Suffixed Output (v1.9.1+)

The migrated OQ-0111 decision in `.qfai/spec/decisions.md` selects one
report per profile. `qfai validate` writes a
profile-suffixed report per profile AND keeps a non-suffixed
`validate.json` pointer that always reflects the most recent run.

### Output paths

```text
.qfai/report/validate-<profile>.json   # one per profile; never overwritten by a different profile's run
.qfai/report/validate.json             # always-latest pointer; explicit `profile: "<name>"` top-level field
```

- `qfai validate --profile prototyping` writes
  `.qfai/report/validate-prototyping.json` AND updates
  `.qfai/report/validate.json` with the prototyping run output (and
  `profile: "prototyping"` at top level).
- Subsequent `qfai validate --profile sdd` writes
  `.qfai/report/validate-sdd.json` AND updates
  `.qfai/report/validate.json` with the sdd run (and
  `profile: "sdd"` at top level). The prior `validate-prototyping.json`
  is **not** overwritten.

### Consumer rule

- Skills that scope by profile (e.g. `certify` scoping to
  prototyping) MUST read the profile-suffixed file
  (`validate-<profile>.json`) rather than `validate.json`. This
  guarantees the read returns the consumer's profile output even when
  a different profile was the most recent run.
- Consumers that only need the most-recent-run snapshot MAY read
  `validate.json` and inspect the explicit `profile` field to confirm
  the expected profile.
- `certify` MUST NOT silently re-run `qfai validate` to refresh the
  pointer (option B was rejected by DR-0001-0008; silent re-run hides
  upstream drift and obscures provenance).

### Deprecation window for `.qfai/output/validate.json`

The legacy path `.qfai/output/validate.json` (documented in pre-1.9.1
skill references such as `handoff.md`) is replaced by
`.qfai/report/validate.json`. During the deprecation window:

- Validators emit `D-DEPRECATED-PATH` (severity: warning) when the
  writer writes the legacy path during the deprecation window, OR
  when a post-sunset stale legacy file is observed on disk; the
  warning text names the sunset version per spec-0003 REQ-0023.
  Read-side tracking (warning when a downstream consumer reads the
  legacy path) is NOT implemented — consumers that still point at
  the legacy path see no file and SHOULD migrate.
- The current implementation writes only to `.qfai/report/`; readers
  that still point at `.qfai/output/` see no file and SHOULD migrate.
- **Sunset version**: qfai 1.10.0 (canonical npm `package.json#version`
  pin). At sunset, the warning escalates to error; the legacy reader
  / writer is removed in the following minor.

### Profiles

- `sdd` runs story structure, contract references, contract validation, per-flow
  grilling evidence and review artifact checks.
- `atdd` runs BF and AC obligations, the BF coverage-depth matrix and ATDD
  evidence checks, scaffold placeholders and acceptance test stubs.
- `tdd` runs the EX obligation, test stubs, contracts and the upstream-edit
  drift check.
- `full` and `verify` combine the stage checks, except the two `drift` families.
- The row-rewritten family runs only in `drift` (OQ-0175).
- The upstream-edit family runs in `tdd` and `drift`, as `QFAI-DRIFT-001` does
  today. `tdd` is the completion gate `/qfai-implement` names, so the
  downstream stage the rule binds sees its own edits there.
- The old-layout error runs in every profile. When it fires, no other
  story-tree family runs: each would report on a tree that is not there, and
  the one sentence that says what to do would be buried.
- A fresh `qfai init` tree holds no BF, US, AC or EX, so the default `full` run
  on it raises no obligation (`qfai-init.md#story-tree-layout`).

The `saas-package` profile runs its prototyping and attestation checks and
emits an info `D-SAAS-PACKAGE-VERIFY-SKIPPED` finding for each omitted stage
gate: `validateStoryTreeObligations` (BF/AC/EX findings 006–009 and scan
failure), `validateStoryTreeCoverageDepth` (131–133),
`validateTestTodoStubs` (`QFAI-TEST-*`) and `validateStoryTreeDrift`
(`QFAI-DRIFT-001`, `QFAI-STORY-010`). The skip notice does not claim those
checks passed.

### Discussion pack

A story-tree project needs no discussion pack. SDD may start from an explicit
user requirement (`story-tree-authoring.md`, BR-0306), and its own preflight
stops when no usable source exists. So a missing pack raises no
`QFAI-DPACK-001` when the configured spec directory holds a story tree and no
pack of any name exists. A misnamed pack still reports `QFAI-DPACK-005` or
`QFAI-DPACK-006`, and `QFAI-DPACK-001` with it. A project with no story tree
still reports `QFAI-DPACK-001` unless it has an import-lite entrypoint.

### What counts as a test

The directory decides a test file's layer, through the crosswalk
`test-layers.md` already declares (`<testsDir>/integration/**`,
`<testsDir>/api/**`, `<testsDir>/e2e/**`) and `packages/qfai/src/core/atddTraceability.ts` already reads.

| Obligation | Satisfied by                                                                                          |
| ---------- | ----------------------------------------------------------------------------------------------------- |
| BF         | A `QFAI:BF-NNNN` annotation in a file under the E2E layer                                             |
| AC         | A `QFAI:AC-NNNN-NNNN-NN` annotation in a file under the integration or API layer                      |
| EX         | A `QFAI:EX-NNNN-NNNN-NN` annotation in a non-E2E file `validation.traceability.testFileGlobs` selects |

An EX annotation under the E2E layer raises `QFAI-STORY-007` and does not
satisfy the EX obligation. The E2E layer carries BF annotations.

These three are the only coverage annotations. The former `QFAI:SPEC-NNNN:`
and `QFAI:CON-API-N` / `QFAI:CON-DB-N` annotations do not satisfy a story-tree
test obligation.

### Flow scope

`--flow` scopes both validate and report to one or more business flows.
Parallel workers can gate separate flows without overwriting one another's
reports.

- **Scope.** `qfai validate --flow BF-NNNN` checks the named flow, its stories,
  their ACs and EXs, and the rules that cite those EXs. The option is
  repeatable, and each value adds its flow.
- **Review packs.** The scope narrows review packs to the flow's
  `business-flow-NNNN/` directory.
- **Output.** `qfai validate` writes `validate.flow-<ids>.json` beside the
  configured `validate.json`, and writes neither `validate.json`,
  `validate-<profile>.json` nor the legacy path. `qfai report --flow` reads
  that file and writes `report.flow-<ids>.md`, or `report.flow-<ids>.json` with
  `--format json`, and only the named flows' per-flow reports. An `--out` path
  wins.
- **A value validate cannot use.** A value that is not a `BF-NNNN` ID, or that
  names a flow the tree does not define, is an error finding naming the value,
  and validate writes no `validate.flow-*.json`.
- **A value report cannot use.** A value that is not a `BF-NNNN` ID exits 2
  before any file is written, so raw input never reaches a file name. When the
  scoped validate result is missing, report exits 2 with its missing-input
  guidance, which names `qfai validate` with the same `--flow` values.
- **Old layout.** `QFAI-LAYOUT-001` prevents story-tree profile validation.
- **Retired option.** `qfai validate --spec` and `qfai report --spec` exit 2
  with guidance to use `--flow BF-NNNN`.

### Rows a validator reads

`decisions.md` and `open-questions.md` keep exactly four columns. A row that a
validator reads says what kind it is at the start of its Content cell: a
keyword, a colon, then the IDs or paths it refers to, separated by commas.
Status alone decides whether the row is in force. Row: the one recording N08,
P3.

| Keyword           | Table               | Refs after the colon                           | In force while | Read by                    |
| ----------------- | ------------------- | ---------------------------------------------- | -------------- | -------------------------- |
| `Test exception:` | `decisions.md`      | BF, AC or EX IDs; the reason goes in Approach  | DONE           | The test-obligation family |
| `Change request:` | `decisions.md`      | Repository-relative paths or IDs it may change | WIP or DONE    | The upstream-edit family   |
| `Unadjudicated:`  | `open-questions.md` | None; the question follows the colon           | TODO or WIP    | `QFAI-SPACK-102`           |

- An exception exempts only the obligation its ID's shape carries: a BF its E2E
  test, an AC its integration or API test, an EX its test. It does not reach
  the BF's stories or the AC's examples.
- An exception naming an ID the tree does not define exempts nothing, so the
  obligation error stays and no other finding is raised.
- `QFAI-SPACK-102` reports an `Unadjudicated:` row at TODO or WIP.
  `QFAI-STORY-003` reports malformed or unreadable story-tree records.

### Drift gate

Both families use the base `QFAI-DRIFT-001` already uses, in every profile
that runs them: `baseBranch` from
`qfai.config.yaml` (default `origin/main`), compared as `<base>...HEAD` by
`packages/qfai/src/core/gitChanges.ts`. When git cannot answer — no base ref,
or not a repository — neither family reports anything, as the upstream guard
does today. When the merge base holds no `decisions.md` at the configured
`paths.specsDir` — the branch that migrates a project, or a project's first
`qfai init` — neither family reports anything: there is no story tree to
protect, and every protected file would read as changed.

- **Protected set:** `01_policy/**` and `02_business-flow/**` under
  `paths.specsDir`, everything under `paths.contractsDir`, `decisions.md` and
  `open-questions.md`.
- **Authorisation:** a change to a protected file needs a `decisions.md` row
  opening `Change request:` that names the file, with Status WIP or DONE. It
  replaces the `## Impact scope` section of `.qfai/decisions/CR-*.md`, which is
  no longer written (REQ-0012).
- **Change-request rows need no authorisation:** a change to `decisions.md`
  confined to `Change request:` rows — appending one at any Status, or changing
  the Status of one — needs no change-request row. Raising a change request
  cannot itself require one, and neither can approving it: a diff against the
  base cannot tell a row appended at TODO and then approved from one appended
  at WIP.
- **Every other change to `decisions.md`** needs a change-request row in force

### Business rules in contracts

A business rule is written in the contract file that enforces it, in the form
the file type allows. The fields are the same in every form: `id` (`BR-NNNN`,
numbered across all contracts), `statement`, and `examples` — one or more full
EX IDs. A contract that relies on a rule another contract defines lists the
rule's ID in a file-level rule-refs list. Row: "A BR with no EX", P3; OQ-0176.

| File type  | Rules                                                                                  | Rule refs                            |
| ---------- | -------------------------------------------------------------------------------------- | ------------------------------------ |
| YAML, JSON | Top-level `x-qfai-rules:`, a list of `{ id, statement, examples: [EX-…] }`             | Top-level `x-qfai-rule-refs: [BR-…]` |
| SQL        | `-- Rule BR-NNNN: <statement>`, followed on the next line by `-- Examples: EX-…, EX-…` | `-- Rule refs: BR-…, BR-…`           |
| Markdown   | A `## Rules` section holding a table with the columns BR-ID, Statement, Examples       | A `Rule refs:` line in that section  |

- The citation runs one way, rule to example. An EX row carries no BR column,
  so "an EX that no rule cites" is computed by reading every rule.
- A rule ref does not count as citing the rule's examples.
- The SQL keys start their line, like `-- Depends on:`, so prose about a rule is
  not read as one. A `-- Rule` line with no `-- Examples:` line after it is a
  rule with no examples, and the BR-to-EX family reports it.

### Text output grammar

This section defines the `--format text` grammar. Message language follows
`.agents/rules/repository-language.md#operator-facing-strings`, with the test
pin in `tests/unit/cliMessageLanguage.test.ts`. What may appear in this output
at all is decided by `.agents/rules/interface-clarity.md`: a terminal is an
interface, and a sentence explaining how to work a command is a defect report
against the command. `tests/cli/commands/validateTextFormat.test.ts` renders
the grammar below and compares it with real output.

#### One issue

Each issue prints one line:

```text
[<severity>] <CODE> <message>[ (<file>)][ refs=<refs>][ suppressed=true]
```

- `severity` is `info`, `warning` or `error`.
- `(<file>)` appears only when the issue has a path.
- `refs=<refs>` appears only when the issue has refs, comma-separated.
- `suppressed=true` appears only when a waiver suppresses the issue.
- `<message>` may contain line breaks and is not normalised, so one issue can
  span several physical lines. The optional slots from `(<file>)` on attach to
  the last of them.
- No timestamp or random value appears in a message, so two runs on the same
  tree print the same text.

Examples:

- `[error] QFAI-DT-002 Circular reference detected: semantic.color.primary (.qfai/spec/03_contract/design/design-tokens.yaml) refs=semantic.color.primary`
- `[error] QFAI-MOCK-002 External URL reference in HTML Mock: https://cdn.example.com/style.css (.qfai/spec/02_business-flow/business-flow-0001/user-story-0001-0001/03_Example.md)`

Some issues are followed by an indented detail block. Whether it prints depends
on the severity and `--fail-on`, not on whether the run fails:

- `error`: always, whatever `--fail-on` is, including `--fail-on never`.
- `warning`: only under `--fail-on warning`, which `--strict` implies.
- `info`: never.

```text
  error_code: <CODE>
  target: <target>
  expected: <expected>
  current: <message>
  fix: <suggested action>
```

Each line starts with two spaces and a label followed by a colon and one space.
A value spanning several lines continues aligned with where the value started:
2 spaces, plus the label's length, plus 2. A block does not always hold five
lines.

```text
  fix: first line of the value
       the next line aligns with the value's first character
```

#### Lines around the issues

In this order, each only where stated:

1. The issues. A test-file scan that stops at its cap or fails prints
   `QFAI-SCAN-002` as an `error` issue, in the grammar above and counted, so
   its missing coverage cannot be mistaken for a passing result. No separate
   warning line is printed.
2. `counts: info=<n> warning=<n> error=<n>` — always. Suppressed issues are not
   counted.
3. `fail-on: <threshold>` — always: the effective `--fail-on` threshold.
4. `timings: over budget <group>=<ms>ms (budget <ms>ms) [<group>=... ...]` —
   only when a validator group ran over its budget. It is not a finding,
   because run time describes the machine rather than the tree.
5. `run-log: <path>` — always, the last line.

#### Classifying a line

Test each line against these rules in order; the first match wins. Structural
lines are tested first, so they are never read as a message continuation.

1. Starts with `[info]`, `[warning]` or `[error]` and a space: a new issue.
2. Starts with `counts:` and a space: the end of the issues.
3. Starts with `fail-on:` and a space: the threshold line.
4. Starts with `timings:` and a space: the over-budget line.
5. Starts with `run-log:` and a space: the last line.
6. The previous issue's severity reaches the run's `--fail-on` threshold and no
   detail block has started: a two-space `error_code:` line starts one. Inside
   a block, a two-space `<label>:` line starts a field and any other line
   continues the previous field.
7. Anything else continues the previous issue's message.

A message continuation ends at rule 1, 2 or 6.

This grammar cannot tell a structural line from a message or field value whose
physical line begins the same way. A reader that needs exact parsing reads the
JSON report at `output.validateJsonPath`.
