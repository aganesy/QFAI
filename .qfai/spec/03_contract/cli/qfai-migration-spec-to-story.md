## No `qfai` subcommand

The migration adds no `qfai` subcommand (`05_Scope.md#Out of Scope` of
`discussion-20260923063306456`, Q12 and Q19 there). The implementation lives in
the `qfai` package, so the scripts reuse `qfai init`'s integration-directory and
managed-block writers rather than copies of them. The skill's `scripts/`
directory holds one thin entry point per step, which loads that implementation
from the package installed in the project.

**Precondition:** the `qfai` package is installed in the project, resolvable
by Node's module resolution from the project root. A script that cannot resolve
it exits 2 and names the install command. `npx qfai` alone does not satisfy it.

## Invocation

Each step is one script, run from the project root:

```text
node <skill-dir>/scripts/<step>.mjs [--dry-run]
```

`<skill-dir>` is the installed skill directory. The only option is `--dry-run`;
any other argument is exit 2.

- **Step 3 exception.** The old slice policy is an archive source only. Its
  original sections do not become current policy. The shipped
  `qfai-sdd/references/sdd-triage.md` owns operation selection, approval,
  impact cascade and ID allocation after migration. Other step 3 sources
  follow their section merge map.
- **Order.** Steps run in number order. A step whose input an earlier step
  produces refuses to run before it, with exit 2 naming that step.
- **The plan.** Splitting a capability into flows is the one judgment a script
  cannot make. The skill writes it to
  `.qfai/evidence/migration-spec-to-story/plan.yaml`: the flow each old user
  story joins, and the contract each business rule goes into. Steps 4 and 7
  read it. A story or rule the plan does not place is listed for a person and
  left where it is.
- **Plan shape.** The document has exactly two top-level lists, `flows` and
  `rules`. A flow is `{ title, from?, stories }`: `title` is a nonempty title;
  `from`, when present, selects one old section of
  `_policies/04_Business-Flow.md`; and `stories` is a list of
  `{ id, criteria? }`. Each `id` is an old user-story ID. `criteria` is a list
  of old acceptance-criterion IDs, needed only where the old AC-to-US
  ownership is ambiguous. An omitted `criteria` uses the old AC references
  only when they identify one story. The old criteria retain their order in
  `03_Acceptance-Criteria.md`, regardless of the order in `criteria`. A rule
  is `{ id, contract }`: `id` is an old business-rule ID and `contract` is a
  path relative to `<paths.contractsDir>`. The order of `flows`, each flow's
  `stories`, and `rules` sets the new ID order. No plan entry uses a new BF,
  US, AC or BR ID.
- **Old-flow selector.** `from` is the exact title of an old level-two heading
  whose title starts with `CHG-` in `_policies/04_Business-Flow.md`, without
  the level-two heading marker. The reserved
  value `_policies/04_Business-Flow.md` selects the unnamed flow before the
  first level-two heading whose title starts with `CHG-` (or the whole file
  when no such heading exists). It is not a BF ID. A specified
  selector must resolve to exactly one section; a missing or repeated heading
  is refused before writing with exit 2. More than one new flow may continue
  the same old section. When `from` is omitted, step 4 uses the shipped
  `business-flow.md` template and lists that new flow under `## For a person`
  with exit 3; it never guesses an old section.
- **Plan validation.** Steps 4 and 7 parse and validate the whole plan before
  their first write. Invalid YAML, unknown or missing fields, wrong types,
  duplicate YAML keys, a repeated story or rule assignment, a criterion
  assigned to two stories, an absent or wrong-kind old ID, or a criterion
  from a different pack than its story is exit 2 naming `plan.yaml` and the
  offending entry.
  A contract path must be a nonempty relative path under
  `<paths.contractsDir>` with a supported YAML, JSON, SQL or Markdown suffix;
  absolute paths, `..` traversal, and paths escaping that directory after
  resolution are exit 2. A valid path to a contract file that does not exist
  is handled by step 7 under `## For a person` with exit 3, leaving its rule
  in the old source. An old AC whose story remains ambiguous without a
  `criteria` assignment is left in its old source and listed under
  `## For a person` with exit 3. An old criterion without a `Scenario` and
  Given, When and Then lines cannot be converted to the new Gherkin row; it
  stays in its old source without a new ID and is listed under
  `## For a person` with exit 3. No invalid plan causes a partial write.
- **The ID map.** Step 4 writes the old-to-new ID map to
  `.qfai/evidence/migration-spec-to-story/id-map.json` once. Steps 5 to 8 read
  it, and a later run of step 4 leaves it unchanged.
- **The plan after step 4.** A step-4 run whose plan places a mapped item
  elsewhere, or places an item the map lacks, exits 2 naming the item. An item
  listed for a person is resolved on the new tree, not by editing the plan.
- **Nothing is deleted.** Step 1 moves each directory entry by entry. An entry
  whose destination exists goes to
  `.qfai/evidence/migration-spec-to-story/legacy/<dir>/` and is listed under
  `## Operations`. A source file whose content has no destination is moved
  whole, by the step that last reads it, to
  `.qfai/evidence/migration-spec-to-story/retired/<spec-id>/`, or to
  `retired/_policies/` for a file under `_policies/`. A directory a step leaves
  empty is removed by that step.
- **The abolished assistant directories.** After moving their content, step 3
  moves every file left under `.qfai/assistant/constitution/`, `catalog/`,
  `manifest/` and `process/` to `retired/assistant/<dir>/`, and removes the
  emptied directories. A `<name>.local.md` overlay moves instead to
  `.qfai/assistant/rule/<name>.local.md` where `rule/<name>.md` exists
  (`qfai-init.md#the-assistant-tree`) and `rule/<name>.local.md` does not.
  One with no such rule, or whose destination already exists, is archived with
  the rest and listed under `## For a person`.
- **A superseded record.** Step 2 writes a superseded record whose successor it
  cannot map — none is named, or the one named is not among the migrated
  records — as a TODO row, and lists it under `## For a person`.
- **Annotations (N15).** Step 8 rewrites a `QFAI:SPEC-NNNN:TC-…` annotation to
  the EX it maps to, and a `QFAI:SPEC-NNNN:US-…` annotation to `QFAI:BF-…` only
  in a file under the E2E layer. A `QFAI:CON-*` annotation, an annotation it
  cannot resolve, and an old deferral marker stay as they are and are reported.
- **Links (E2 of the discussion record).** Step 9 inspects all six host
  integration paths before writing. An inspection failure exits 2 with no
  write. It repoints managed links to the singular directories and changes
  nothing else. An occupied user-owned wrapper or obsolete roster is left
  unchanged and listed under `## For a person` with exit 3. It does not run
  `qfai init --force`. A missing or wrong-kind canonical skill or agent source leaves its host
  wrapper unchanged. Step 9 lists the wrapper and source under
  `## For a person` with exit 3; it does not create a dangling link.
- **The drift gate.** A migration branch's base holds no story tree, so
  neither drift family reports on it (`qfai-validate.md#drift-gate`). Step 2
  writes no change-request row for the migration, and a migrated
  `Change request:` row keeps the paths its record named.

## `--dry-run`

A dry run writes nothing and prints every operation the real run would
perform, in the order it would perform them. Its printed operations match the
files the real run changes (NFR-0002).

## Idempotency

A second run of any step on a tree it already migrated changes no file. A run
that was interrupted completes when run again (NFR-0001).
If staging ownership cannot be verified, or its payload changed after the
interruption, the step leaves it in place and reports it for a person to
resolve. It does not infer ownership from a filename alone.

## Write set

A script writes only what its step needs, and only inside this set (NFR-0008).
It makes no network call. The new tree is written into the configured
`paths.specsDir` and `paths.contractsDir`, wherever a project has put them, so
NFR-0008's write list includes both.

| Target                                                                                                                                                                                                                                                  | Steps |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----- |
| `.qfai/`, and the configured `paths.specsDir` and `paths.contractsDir` where they lie outside it                                                                                                                                                        | 1–7   |
| `qfai.config.yaml`                                                                                                                                                                                                                                      | 1, 3  |
| The managed block of `.gitignore`                                                                                                                                                                                                                       | 10    |
| The host integration links: `.claude/skills`, `.agents/skills`, `.codex/skills`, `.github/skills`, `.claude/agents`, `.github/agents`                                                                                                                   | 9     |
| `QFAI:` annotation lines in test files                                                                                                                                                                                                                  | 8     |
| Temporary staging under `.qfai/evidence/migration-spec-to-story/staging/`, or under the configured `paths.specsDir`, `paths.contractsDir`, or `paths.testsDir` as `.qfai-migration-staging/` when a destination needs a staging file on the same volume | 1–8   |
| Temporary `.qfai/report/.gitignore-<pid>-<UUID>.tmp` and `.owner` files used for the atomic managed-block update                                                                                                                                        | 10    |

Staging holds only files owned by the current operation. A completed step removes
its staging files. After an interruption, the same step verifies ownership and
resumes or removes its own staging files before applying the remaining plan.
The step 10 `.owner` marker records the staged payload's size and SHA-256 digest;
a missing, incomplete or mismatched marker does not authorize deletion.
For step 8, the persistent change to a test file is limited to its annotation
lines; the temporary staging copy is not an additional test artifact.

## Exit codes

| Code  | Meaning                                                                                                                                                                                                                                                                                    |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 0     | The step is complete and nothing needs a person                                                                                                                                                                                                                                            |
| 2     | Refused before writing: an unknown argument, not run at a project root, the package cannot be resolved, an earlier step has not run, an input cannot be read or parsed, the plan is invalid or disagrees with the ID map, or step 9 cannot inspect an integration path. Nothing is written |
| 3     | The step is complete and its report lists items a person must resolve                                                                                                                                                                                                                      |
| Other | An unexpected failure. The step can be run again (`## Idempotency`)                                                                                                                                                                                                                        |

## Report

Each script prints its report on standard output as Markdown, in a dry run and
a real run alike. It writes no report file, so a second run changes no file.
The skill keeps the reports in its own evidence. A section with nothing in it
is printed with the word `none`, so an empty section and a missing one are not
confused.

| Section                | Printed by | Lists                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ---------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `## Operations`        | Every step | Each operation performed, or in a dry run to be performed: the path and what happens to it                                                                                                                                                                                                                                                                                                                                                                                                        |
| `## Cases to examples` | 5          | Each `06_Test-Cases` row with no EX, with its old TC ID and its new EX ID (REQ-0020)                                                                                                                                                                                                                                                                                                                                                                                                              |
| `## For a person`      | 2 to 10    | Every item the step could not settle, with its file and the reason: a superseded record whose successor it cannot map, an overlay with no rule to sit beside or whose place beside it is taken, a TC row citing several ACs, an EX with zero or several derived ACs, a story or rule the plan does not place, an annotation it could not resolve, a user-owned wrapper or obsolete roster that step 9 preserved, or staging that step 10 cannot verify as its own. Nothing listed here is dropped |
| `## Annotations kept`  | 8          | Every `QFAI:SPEC-NNNN:US-…` annotation outside the E2E layer, every `QFAI:CON-*` annotation, and every old deferral marker, with the file and line                                                                                                                                                                                                                                                                                                                                                |

The number of `06_Test-Cases` rows with no EX in the input equals the number of
entries across `## Cases to examples` and the TC rows in `## For a person`
(NFR-0003).

After step 10 the skill runs `qfai validate`. Its test-obligation findings
(`qfai-validate.md#story-tree-layout`) are the list of every BF, AC and EX left
without a test at its layer, and the migration is complete when it reports no
layout or chain error (REQ-0019, DSC-003).
