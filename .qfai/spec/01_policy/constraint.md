# Constraints

## Technical Constraints

| ID    | Constraint                                                                                                                                                                                                                                                                                                                               | Rationale                                                                                                                                                    |
| ----- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| TC-01 | The package runs on the Node.js floor it declares, on Linux and on Windows.                                                                                                                                                                                                                                                              | Adopters install it on either platform, on any Node.js release from that floor up.                                                                           |
| TC-02 | Validation is deterministic: the same tree and the same configuration give the same findings.                                                                                                                                                                                                                                            | A result has to be reproducible, and comparable between runs and between machines.                                                                           |
| TC-03 | Every stage after the specification stage reads the story tree and its contracts, never a discussion pack, and a missing contract is never filled from discussion material.                                                                                                                                                              | The discussion pack is discovery evidence upstream of the specification; a check that accepted it in place of a contract would pass what no contract states. |
| TC-04 | The published package carries no identifier only this repository understands.                                                                                                                                                                                                                                                            | An adopter cannot open the documents such an identifier points at.                                                                                           |
| TC-05 | Every spec-tree document conforms to its closed schema, and no schema is loosened.                                                                                                                                                                                                                                                       | A document that passes its schema can be read and checked without guessing its shape.                                                                        |
| TC-06 | The traceability chain BF → US → AC → EX → Test → Code and its validate checks stay as they are.                                                                                                                                                                                                                                         | The chain is what lets a finding name the item and the test that owe each other.                                                                             |
| TC-07 | qfai init and qfai doctor never delete a retired path their leftover check lists: the evidence, review and run trees, the asset lock, the install-provenance record and the retired discussion-pack files. They list it. Every other deletion follows its command contract, and the v1-to-v2 migration deletes only what cli-0010 names. | Such a path may hold the only copy of something the adopter needs; the migration says so before its first real run.                                          |

## Operational Constraints

| ID    | Constraint                                                                                                                                                                                                                                                                                                                                                                                                                                          | Rationale                                                                                                                     |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| OC-01 | Every check CI runs is one a contributor can run locally.                                                                                                                                                                                                                                                                                                                                                                                           | A local run of the same checks then predicts the CI result.                                                                   |
| OC-02 | Shared history is never rewritten.                                                                                                                                                                                                                                                                                                                                                                                                                  | Rewriting a branch that other work builds on loses that work.                                                                 |
| OC-03 | Settings that live outside the repository, such as branch protection and the package registry's trusted publishing, are changed only by an administrator, and the repository declares what it expects of them.                                                                                                                                                                                                                                      | No pull request can read or change such a setting, so the repository can only state its expectation and hand the change over. |
| OC-04 | A contract or recorded decision that states removed behaviour changes only through a change request row the user approved. A row of the decisions or open-questions table keeps its ID, Content and Approach and is never removed; only its Status moves, as the register rules set out. A row a later row wholly supersedes is marked SUPERSEDED (by DEC-NNNN); a row superseded in part keeps its Status, and the superseding row names the part. | A new row supersedes an old one rather than rewriting it, and the Status says which rows are in force.                        |
| OC-05 | A change made of several areas ships as one pull request per area under one parent issue, merged into one release branch in dependency order.                                                                                                                                                                                                                                                                                                       | Each area is reviewed on its own, and the release holds them together.                                                        |

## Business Constraints

| ID    | Constraint                                                                                                                                               | Rationale                                                                                     |
| ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| BC-01 | A breaking change ships with release notes that say what breaks and how an adopter migrates.                                                             | Adopters upgrade from the published package and learn of a break only from its release notes. |
| BC-02 | The lighter workflow ships as release 2.1.0, which the user chose knowing it breaks earlier behaviour, and its release notes list every breaking change. | The user decided the version; the release notes are how an adopter learns what broke.         |
