# Glossary

## Terms

| Term                                | Definition                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| active discussion pack              | The one discussion pack the project is working from, recorded in QFAI's state file and chosen with `qfai discussion use`. When none is recorded and several exist, QFAI refuses to guess and names the candidates.                                                                                                                                                                                                           |
| adopter file state                  | The state of one shipped workflow file in an adopter's repository, from the closed set in `03_contract/cli/cli-0020-shipped-workflows.md`. The record of what QFAI wrote is what tells a file never installed from one the adopter removed on purpose, which QFAI never re-creates.                                                                                                                                          |
| aggregate verdict                   | The single always-run CI job that reports one result for every lane. It derives the result from the jobs it depends on, not from a list in its own body. The dangerous failure is a green result when nothing ran, so it is tested for failed, cancelled, all-succeeded and all-skipped inputs.                                                                                                                              |
| attempt                             | One try at a stage instance. A retry is a new attempt of the same stage instance and counts against the retry budget in `cli-0017-qfai-workflow.md#state-machine`.                                                                                                                                                                                                                                                           |
| authorization kind                  | What permits a run to act. There are three kinds: the request's own scope, for the normal change it allowed; a recorded human decision, for the one question it answers; and a project policy, for an external effect the policy names (`03_contract/cli/cli-0017-qfai-workflow.md#authorizations`). The request's scope never raises a decision-table row to WIP, and a human decision is not an envelope-deviation record. |
| autopilot policy                    | The section of every stage skill that says which decisions the skill takes itself, which it asks the operator, and which inputs it must be given. A skill may narrow a category but never adds one. The categories are in `03_contract/cli/cli-0001-assistant-routing.md`.                                                                                                                                                   |
| business flow (BF)                  | An ordered sequence of activities a user performs to reach an outcome. It is the top of the concrete layer, and its stories hang under it. Its ID is `BF-NNNN`. A flow follows what a user does, not what the product offers, so it is not a capability.                                                                                                                                                                     |
| business rule (BR)                  | A rule the product enforces, written in the contract that enforces it and citing at least one example that shows it. A rule spanning several contracts lives in the authoritative one, and the others cite it. The ID and field rules are in `03_contract/cli/cli-0021-story-tree-authoring.md`.                                                                                                                             |
| capture contract                    | The capture settings an iteration plan declares for each screen when capture is on: the viewport, the device scale, when the page counts as loaded, and how its HTML is copied. The fields are in `03_contract/cli/cli-0014-qfai-prototyping-iterate.md`.                                                                                                                                                                    |
| change detection                    | The CI job that works out from the base-to-head diff which lanes a change needs. It is the only job that needs the full history. When it cannot read the diff, or meets a path it does not recognise, it selects every lane.                                                                                                                                                                                                 |
| change-derived lane selection       | Running or skipping each CI lane from what change detection found. Every lane stays declared; one not selected is skipped by a false condition, so its check name still reports and it uses no runner time. Removing the lane from the matrix instead would make its check name disappear.                                                                                                                                   |
| completion target                   | What a run must reach before it reports completion: a change made and verified in the working tree, or that plus QFAI's delivery conditions, which `finish` judges (`03_contract/cli/cli-0017-qfai-workflow.md#completion`). A working-tree result is never reported as the fuller target.                                                                                                                                   |
| concrete layer                      | `02_business-flow/`: flows, stories, acceptance criteria and examples. Written in full before any contract.                                                                                                                                                                                                                                                                                                                  |
| concrete-first                      | The order `/qfai-sdd` writes in: policy, business flows, stories with their acceptance criteria and examples, then the contracts and their business rules.                                                                                                                                                                                                                                                                   |
| contract layer                      | `03_contract/`: the machine-checkable layer derived from the concrete layer — the contract index, the technology contract, and the API, database, UI, CLI and design contracts. Business rules live here, each in the contract that enforces it.                                                                                                                                                                             |
| contract readiness                  | The state in which a project's design and UI contracts hold the minimum a later stage needs to run. The design-contract readiness check in `qfai validate` judges it.                                                                                                                                                                                                                                                        |
| design-system contract              | The root `DESIGN.md` of a UI project, which holds its brand design tokens. The prototyping loop and `/qfai-implement` read the tokens from that file; nothing copies them.                                                                                                                                                                                                                                                   |
| discussion pack                     | The requirements and discovery record `/qfai-discussion` writes before any specification exists. `/qfai-sdd` reads it as input; later stages read the story tree and its contracts instead.                                                                                                                                                                                                                                  |
| envelope-deviation record           | The local record written when the operator answers a question about leaving a skill's envelope: its scope, an architectural decision, re-adopting a rejected option, or widening the scope. `qfai audit log` lists these records.                                                                                                                                                                                            |
| EX-to-AC link                       | The citation from an example to the one acceptance criterion it illustrates. Every acceptance criterion has at least one example.                                                                                                                                                                                                                                                                                            |
| exploration-first                   | The posture in which discussion carries the screen explorations unranked and prototyping explores, compares and converges them. The brand direction is outside it: the user chooses it during discussion.                                                                                                                                                                                                                    |
| fail-closed                         | Refusing to report success when an input cannot be read. It is right when continuing would substitute an input the result depends on. In the shipped workflows the one case is resolving the package manager: nothing is installed, so any result would describe work that never ran. Not the run cause of the same name (fail-closed (run)).                                                                                |
| fail-closed (run)                   | A cause that stops automatic chaining until it is cleared through `resume` or the run is stopped. It never rewrites the project's configuration (`03_contract/cli/cli-0017-qfai-workflow.md#fail-closed`). Not the CI sense of fail-closed, which refuses to report success when an input cannot be read.                                                                                                                    |
| fail-open                           | Continuing with a wider, conservative run when an input cannot be read, and saying so in an annotation. It is right when the wider run cannot claim something that was never checked: a failed diff is treated as "everything changed", so lanes only over-run. The test is whether the degraded run could report green for something it did not establish, not what it costs.                                               |
| frozen surface union                | Every screen declared by any UI contract a prototyping run covers, fixed at the start of the run. Each screen in it must end the run with both a screenshot and an HTML snapshot.                                                                                                                                                                                                                                            |
| green-on-skip                       | The aggregate verdict reporting success when every lane was legitimately skipped. Without it a pull request that needs no lane would fail. Because a skipped job reports success, a job that carries a required status check must never be one that can be skipped.                                                                                                                                                          |
| handoff                             | The state one skill leaves for the next, in the single shape every skill writes (`03_contract/cli/cli-0001-assistant-routing.md`). It is separate from the prototype handoff, which carries the prototyping result to implementation.                                                                                                                                                                                        |
| harness                             | The host session, such as Claude Code or Codex, that runs the agents, commands and tests and calls `npx qfai workflow`. The CLI never starts it. Not a test harness.                                                                                                                                                                                                                                                         |
| layer-separated test lane           | A CI lane — one job or one matrix leg — that runs one test layer: unit, component, integration, API or end-to-end. A lane is a CI term, a layer is a test term, and a slice is a leg of QFAI's own test matrix; the three are not interchangeable. Lanes are jobs inside one workflow file, because a new file creates a new check name, and check names are a repository setting an agent cannot change.                    |
| layout anti-pattern                 | A structural defect in a prototype screen, such as a page nothing links to, a flow with no way back, or two screens that capture identically. The prototyping review reports each by its catalogue ID; the catalogue and its effect on the information-architecture score are in `03_contract/cli/cli-0013-qfai-prototyping.md`.                                                                                             |
| mutation log                        | The append-only record of every delete or overwrite of a prototyping iteration's evidence. Code that changes that evidence without writing to the log is a finding (`03_contract/cli/cli-0014-qfai-prototyping-iterate.md`).                                                                                                                                                                                                 |
| obligation set                      | The business flow, acceptance criterion and example IDs of the flow a run binds, with whether a test annotates each example. A stage processes the examples no test annotates. It is not a ledger: nothing records it apart from the tree and the tests.                                                                                                                                                                     |
| operator                            | The person who types the request and answers the run's questions.                                                                                                                                                                                                                                                                                                                                                            |
| orchestrated mode                   | A stage skill running because `qfai-run` handed it a valid work order. It takes the binding instead of asking again, runs only the steps the work order names, and ends where the work order ends. The entry check is in `.qfai/assistant/rule/shared-skill-operating-baseline.md#workflow-run-entry-check-mandatory`.                                                                                                       |
| patch zone                          | The part of `DESIGN.md` that may change without invalidating the prototyping evidence frozen against it. An edit outside it, or removing it, invalidates that evidence (`03_contract/cli/cli-0013-qfai-prototyping.md`).                                                                                                                                                                                                     |
| policy layer                        | `01_policy/`: the objective, initiative, principles, glossary and constraints. It states principles and criteria, never a concrete definition.                                                                                                                                                                                                                                                                               |
| prototyping mode                    | Whether a prototyping iteration works toward a certifiable result (convergence, the default) or explores shallowly across several contracts (exploration). An exploration iteration relaxes some gates and is never certified; the differences are in `03_contract/cli/cli-0013-qfai-prototyping.md`.                                                                                                                        |
| receipt                             | The record that a stage result or a gate result was accepted, with its fingerprint, its dependencies and its trust level (`03_contract/cli/cli-0017-qfai-workflow.md#fingerprints-and-receipts`). It points at the run's copy of `verify.json` rather than being that file.                                                                                                                                                  |
| reserved filename prefix            | The `qfai-` prefix of every shipped workflow file name. It announces the names QFAI may use, so a clash can be foreseen. It never decides which files QFAI owns: an adopter may have written a file with the same prefix.                                                                                                                                                                                                    |
| route (workflow)                    | The workflow a change request takes, resolved to a plan the package ships (BR-0022-0010). Routes do not replace the change types of `workflow.md`. Not the screen route a UI contract declares.                                                                                                                                                                                                                              |
| run                                 | One operator request carried through `npx qfai workflow`, from `start` to a terminal state. Its runtime state and local run records are laid out in `03_contract/cli/cli-0022-workflow-files.md`; its states are in `03_contract/cli/cli-0017-qfai-workflow.md#state-machine`.                                                                                                                                               |
| runner-label indirection            | Reading a CI job's runner label from a repository variable whose default is a public GitHub-hosted label. A private label never appears in a shipped file. An unknown label makes GitHub queue the job indefinitely rather than fail, so a sound default matters more than the ability to change it.                                                                                                                         |
| saas-package profile                | A lighter verification scope for a project delivered as a SaaS package. It requires the prototyping checks and a design-system attestation, skips the ATDD and implementation gates, and its certificate names what it skipped and never claims full completion (`03_contract/cli/cli-0016-qfai-validate.md`).                                                                                                               |
| shipped-workflow ownership contract | The contract that fixes which files QFAI may write, refresh or remove in an adopter's workflows directory (`03_contract/cli/cli-0020-shipped-workflows.md`). The names come from lists inside the package and from a record of what QFAI itself wrote; a file with no record belongs to the adopter and is never touched.                                                                                                    |
| stage instance                      | One execution of a stage, such as acceptance, inside a run. The `implement-seam` round trip returns to the same stage instance. It is not a step inside one skill, such as the preflight of `/qfai-sdd`.                                                                                                                                                                                                                     |
| standalone mode                     | A stage skill invoked by name by the operator. It runs that stage alone and ends there.                                                                                                                                                                                                                                                                                                                                      |
| step                                | One part of a stage skill's procedure, kept at `.qfai/assistant/step/<name>/STEP.md` and run by the skill that lists it in `steps:` or by a work order that names it. No host lists a step as a skill (`03_contract/cli/cli-0002-assistant-steps.md`). It is neither a skill nor a Stage of `/qfai-sdd` in its own procedure.                                                                                                |
| story tree                          | The layout of the specification under `.qfai/spec/`: the decision and open-question tables, the policy layer, the concrete layer and the contract layer. It carries the chain business flow → user story → acceptance criterion → example, and each business rule cites the examples it enforces.                                                                                                                            |
| target binding                      | The business flow a work order acts on, or a `new_story` slot until the story-authoring stage creates the story and binds its IDs. It is never absent from a stage that takes a target (`cli-0017-qfai-workflow.md#work-order`).                                                                                                                                                                                             |
| test exception                      | A decision-table row, opening `Test exception:`, that exempts named business flows, acceptance criteria or examples from the test their kind requires, with the reason. It holds only while its status is DONE, and it reaches nothing below the IDs it names.                                                                                                                                                               |
| UI contract                         | A contract in the contract layer's `ui/` directory that declares the screens and routes of a project with a UI.                                                                                                                                                                                                                                                                                                              |
| UIUX sidecar                        | The UI and UX files a discussion pack carries beside its main documents. They record design intent for `/qfai-sdd` to translate; no later stage reads them directly.                                                                                                                                                                                                                                                         |
| UX axis                             | One of the four ordinal scores the prototyping review gives a set of screens: information architecture, navigation flow, usability and functionality. The scale and its caps are in `03_contract/cli/cli-0013-qfai-prototyping.md`.                                                                                                                                                                                          |
| verification scope                  | Which stage's obligations a verification result covers: prototyping only, ATDD only, or all stages. A prototyping certificate accepts only a prototyping-scope result, so the prototyping stage can finish before the later stages have produced anything. The values are in `03_contract/cli/cli-0013-qfai-prototyping.md`.                                                                                                 |
| work order                          | The unit the control core issues through `next` to one stage: the run, stage instance, attempt, steps, target, scope, obligation set, required reviewers and actor history (`03_contract/cli/cli-0017-qfai-workflow.md#work-order`). It is not a delegation an orchestrator makes inside one stage.                                                                                                                          |
| worker-scoped credential reuse      | Caching one signed-in session per test worker and actor, reusing it for every test that worker runs, discarding it when the worker ends, and signing in again when the saved session is refused. It is safe because a worker runs its tests one at a time. The guidance names no browser tool.                                                                                                                               |
| workflow mode                       | The project setting that decides whether `npx qfai workflow` creates runs; an absent setting means it does (`03_contract/cli/cli-0017-qfai-workflow.md#modes`). Not `--auto`, which is a skill's no-question mode and never an approval.                                                                                                                                                                                     |
