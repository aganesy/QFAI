# Glossary

## Terms

| Term                              | Definition                                                                                                                                                                                                                                                                                                                                            |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| discussion pack                   | `/qfai-discussion` が生成する upstream requirements/discovery artifact。`/qfai-sdd` の入力専用。                                                                                                                                                                                                                                                      |
| exploration-first                 | The posture in which discussion carries the screen explorations unranked and prototyping explores, compares and converges them. The brand direction is outside it: the user chooses it during discussion.                                                                                                                                             |
| UIUX sidecar                      | discussion pack 配下の `uiux/*.md` 群。design intent の authoring artifact であり downstream execution truth ではない。                                                                                                                                                                                                                               |
| design-system contract            | A `design-system.yaml` mirror of the frozen root `DESIGN.md` tokens, governed under `.qfai/spec/03_contract/design/` for a UI-bearing project. It is mirrored from root `DESIGN.md` after the prototyping loop.                                                                                                                                       |
| breakthrough evidence             | `.qfai/evidence/breakthrough.json`。plateau detector 判定、trigger reasons、branch 実行証跡の SSOT。                                                                                                                                                                                                                                                  |
| UI contract                       | A screen and route contract under `.qfai/spec/03_contract/ui/*.yaml` for a UI-bearing project.                                                                                                                                                                                                                                                        |
| direct discussion-pack validation | discussion pack root を明示的に入力して canonical UIX validators を回すこと。repo-root downstream validate と区別する。                                                                                                                                                                                                                               |
| best-of-history                   | 後続 iteration が常に最良とはみなさず、過去勝者を incumbent と比較し続ける運用。                                                                                                                                                                                                                                                                      |
| plateau detector                  | `allReviewerAxesPerfect100`, score delta, diff lines を使って breakthrough branch を機械判定で発火するロジック。                                                                                                                                                                                                                                      |
| mandatory UI evidence             | `.qfai/evidence/prototyping/screenshots/<screen-id>.png` と `.qfai/evidence/prototyping/html/<screen-id>.html`。declared screen ごとに両方必須。                                                                                                                                                                                                      |
| contract readiness                | design/ui contracts が downstream execution に必要な最小 schema を満たしている状態。                                                                                                                                                                                                                                                                  |
| DESIGN.md                         | Root `DESIGN.md`: the SSOT for brand vision and visual identity (color, font, radius and shadow tokens). `/qfai-sdd` authors it from the brand direction the discussion pack records, and freezes its sha256 in the contract step.                                                                                                                    |
| designMdViolations                | (UX-loop redesign / spec-0012) iter HTML が `DESIGN.md` token から逸脱している箇所のリスト。`{category, expected, found, location}` の配列。`findDesignMdViolations(html, designMd)` (pure function) が出力。非空時は convergence (exit 64) を block する。                                                                                           |
| layoutAntiPatterns (lap-\*)       | (UX-loop redesign / spec-0012) UI 構造的 anti-pattern の集合 `{lap-001-orphan-page, lap-002-deadend-flow, lap-003-modal-stack-trap, lap-004-hidden-primary-action, lap-005-no-empty-state, lap-006-mystery-meat-icon, lap-007-state-not-represented, lap-008-no-back-affordance}`。検出時に informationArchitecture を `acceptable` 以下に cap する。 |
| informationArchitecture (axis)    | (UX-loop redesign / spec-0012) UX 評価軸の 1 つ。ordinal `{weak, acceptable, strong, exceptional}`。情報の階層・グルーピング・wayfinding がどれだけ user に明確かを評価する。lap-\* 検出時は `acceptable` cap。                                                                                                                                       |
| navigationFlow (axis)             | (UX-loop redesign / spec-0012) UX 評価軸の 1 つ。primary task の達成までの経路がどれだけ短く明示的かを評価する。                                                                                                                                                                                                                                      |
| usability (axis)                  | (UX-loop redesign / spec-0012) UX 評価軸の 1 つ。tap target / contrast / state visibility / error recovery の総合評価。                                                                                                                                                                                                                               |
| originality (axis) [DEPRECATED]   | (UX-loop redesign / spec-0012) 旧 4 軸の 1 つ。informationArchitecture に置換された。history-only。                                                                                                                                                                                                                                                   |
| designQuality (axis) [DEPRECATED] | (UX-loop redesign / spec-0012) 旧 4 軸の 1 つ。navigationFlow に置換された。history-only。                                                                                                                                                                                                                                                            |
| craft (axis) [DEPRECATED]         | (UX-loop redesign / spec-0012) 旧 4 軸の 1 つ。usability に置換された。history-only。                                                                                                                                                                                                                                                                 |
| slopPatternsDetected [DEPRECATED] | (UX-loop redesign / spec-0012) `iter-NN/review.json` の旧フィールド。`layoutAntiPatternsDetected` に置換された。history-only。                                                                                                                                                                                                                        |

### CHG-007 (Layered CI Test Scaffold Adoption, 2026-08-05)

定義は discussion-20260804173914356 `08_Glossary.md` の TERM-004/009/012/014/015/017/018/023/026 と一致させる。レイヤー語彙は増やさない（NFR-0015）: 新しいテストレイヤートークンは導入せず、既存の L1..L5（Unit / Component / Integration / API / E2E）のみを使う。

| Term                                | Definition                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| aggregate verdict (集約 verdict)    | 全レーンの結果を代表する常時実行（`if: always()`）の単一 job とその判定。verdict は job body に列挙された比較リストではなく、その job 自身の `needs` 集合から**導出**される (REQ-0006)。危険な故障モードは失敗ではなく **vacuous success**（何も走っていないのに green）なので、failed / cancelled / all-succeeded / all-skipped の 4 状態すべてに対してテストされる。混同注意: 集約 verdict は**必須ステータスチェックではない** — 実測 (DTC-28) では必須コンテキストは `build` job であり、移設は `OQ-0022` で deferred。                                                                                                                        |
| change detection (変更検知)         | base..head 差分からどのレーンを走らせるかを導出する job。full history を要求するのはこの job のみ。差分取得失敗と未認識パスでは fail-open する。QFAI の除外集合は移植元と異なる: assistant tree は validate 出力を変える**ため documentation-only ではなく**、agent-integration mirror は documentation-only 扱い。                                                                                                                                                                                                                                                                                                                                |
| change-derived lane selection       | 変更検知の出力からレーンごとの実行可否を決める方式。全レーンは常に**宣言**されたままで、非選択レーンはレーン定義の削除ではなく **false 条件による skip** で表現される。したがって leg の check name は消えず、skip されたレーンは runner minutes を消費しない (REQ-0007 / REQ-0017)。混同注意: matrix を空にする / leg を削る方式とは別物であり、後者は check name を消滅させるため rejected shape。                                                                                                                                                                                                                                               |
| layer-separated test lane           | 1 つのテストレイヤー（L1 unit / L2 component / L3 integration / L4 api / L5 e2e）に対応する CI lane（1 job または 1 matrix leg）。**lane は CI 概念、layer はテスト意味論の概念、slice は QFAI 自身の matrix 次元**であり、3 つは決して交換可能に使わない。レーン分離は新規ワークフローファイルではなく同一ファイル**内の job**として表現する — 新しいワークフローファイルは新しい check name を生み、check name はエージェントが設定できないリポジトリ設定面だから (REQ-0008 / REQ-0016)。新しいレイヤートークンは追加しない (NFR-0015)。                                                                                                         |
| runner-label indirection            | runner セレクタを public な GitHub-hosted ラベルを既定値とする repository variable 経由で読む方式。organization-private ラベルは配布物に一切現れない。未知のラベルは fail fast せず GitHub が**無期限にキューする**ため、可変にすること（knob）より既定値の妥当性のほうが load-bearing。各配布ファイルは変数名・既定値・誤設定時の故障モードを header table に明示する (REQ-0018)。                                                                                                                                                                                                                                                                |
| shipped-workflow ownership contract | QFAI がアダプタの workflows ディレクトリ配下で**書き込み・refresh・prune してよいファイル集合**を宣言しテストで固定した契約（`CLI-WFSET`）。write-set は QFAI が現在配布する name の列挙、prune-set は過去バージョンが配布した name の列挙であり、いずれもバイナリ内の名前リストで決まる。name だけでは不十分なため provenance 記録（QFAI 自身が書いたファイルの記録）を伴い、記録のないファイルは adopter 所有として不可触。あらゆる refresh / stale 除去の前提条件 (REQ-0020)。                                                                                                                                                                  |
| `qfai-` prefix (reservation notice) | 配布ワークフローのファイル名 prefix `^qfai-[a-z0-9-]+\.yml$`。**予約の告知であって selector ではない** — 衝突を「予見可能」にするために文書化されるが、書き込み対象・prune 対象の判定に prefix glob を使うことは禁止される。混同注意: prefix に一致するファイルをアダプタが正当に自作している可能性があるため、prefix 一致を所有の証拠として扱うと adopter のファイルを奪う (`CLI-WFSET`)。                                                                                                                                                                                                                                                        |
| adopter file state (5-state enum)   | 配布ワークフロー 1 ファイルのアダプタ側状態を表す**閉じた 5 値**: `absent`（未インストール。provenance 記録も無い）/ `adopter-owned`（QFAI が書いた記録が無く、アダプタ所有と判定）/ `installed`（記録あり・未改変）/ `modified`（記録あり・改変済み。drift として名指しするが黙って上書きしない）/ `declined`（QFAI が入れた後アダプタが削除 — 再作成せず、stale 報告もせず、prune もしない）。混同注意: `absent` と `declined` は provenance 記録の有無だけで区別され、これを取り違えるとアダプタが意図的に消したファイルの復元を勧告してしまう。列挙は閉じており、consumer 側（init / doctor）が独自 state を追加してはならない (`CLI-WFSET`)。 |
| worker-scoped credential reuse      | 認証済みセッションを **worker index と actor の対** をキーにして 1 つだけキャッシュし、その worker 内の全テストで再利用し、worker 終了時に破棄し、復元セッションが拒否されたら再認証してキャッシュを書き直す運用ルール。worker はテストを直列実行するので、worker 単位のキャッシュは同時利用されない — これがルールの成立根拠。backend 非依存の ATDD レイヤーガイダンスとして記録され、ブラウザ backend を一切名指ししない (REQ-0024)。QFAI 自身のスイートは credential を 0 個使うので dogfood されない。                                                                                                                                         |
| fail-open                           | 入力取得に失敗したとき、annotation を出して**本来より広い（保守的な superset の）作業**を続行すること。判断基準はコストではなく「degraded な実行が、確立していないことを green で主張してしまうか」。差分取得失敗は「全部変わったと仮定する」なので over-run しかせず該当する。shallow clone / base ref 不在 / optional script 不在 / Node version file 不在も同クラス。                                                                                                                                                                                                                                                                           |
| fail-closed                         | 入力取得に失敗したとき、success の報告を拒否すること。degrade が判断の依存**入力を差し替える**場合に正しい。配布セットでの唯一の該当箇所はパッケージマネージャ解決 — 何もインストールされないため、続行は評価していない結果の報告になる。verdict job と failure threshold も同クラス。混同注意: 「runner minutes しか失わない」というコスト論は失敗した install にも当てはまるため、コスト基準では誤答になる。                                                                                                                                                                                                                                     |
| green-on-skip                       | matrix が正当に空だった（＝全レーンが skip された）ときに verdict が success を報告する性質。これがないと変更検知は zero-work な pull request を red にするため運用不能になる。混同注意: skip された job は success を報告するので、**必須ステータスコンテキストを担う job を選択対象にしてはならない** — 走っていない job に対して branch protection へ green を渡すことになる。                                                                                                                                                                                                                                                                  |

### Spec-to-story restructure (2026-09-23)

Terms of the story-tree layout released as 2.0.0 (`07_Constraints.md` OC-82). The spec-pack terms above are retired when this layout replaces the old one at the P7 cutover.

| Term                 | Definition                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| business flow (BF)   | An ordered sequence of activities a user performs to reach an outcome. The top of the concrete layer; its stories hang under it. ID `BF-NNNN`, directory `02_business-flow/business-flow-NNNN/`. Not a capability: a flow follows what a user does, not what the product offers.                                                                                                                                                                                        |
| story tree           | The layout under `.qfai/spec/` that replaces the spec pack: `decisions.md`, `open-questions.md`, `01_policy/`, `02_business-flow/` and `03_contract/`. A story directory `user-story-NNNN-NNNN/` holds exactly `01_User-story.md`, `02_Acceptance-Criteria.md` and `03_Example.md`. The chain it carries is BF → US → AC → EX ← BR.                                                                                                                                     |
| policy layer         | `01_policy/`: objective, initiative, principle, glossary and constraint. States principles and criteria, and no concrete definition. Not the spec-pack layout's `_policies/`.                                                                                                                                                                                                                                                                                           |
| concrete layer       | `02_business-flow/`: flows, stories, acceptance criteria and examples. Written in full before any contract.                                                                                                                                                                                                                                                                                                                                                             |
| contract layer       | `03_contract/`: the machine-checkable layer derived from the concrete layer — `contracts.md` (the index), `tech.md`, `structure.md`, and `api/`, `db/`, `ui/`, `cli/`, `design/`. Contract IDs such as `CON-API-NNNN` do not change. Business rules live here.                                                                                                                                                                                                          |
| concrete-first       | The `/qfai-sdd` order: policy, business flow, stories (US, AC, EX), then contracts with their BRs. Replaces contracts-first, which wrote the contracts before the outline and the slices.                                                                                                                                                                                                                                                                               |
| EX-to-AC link        | Each example cites exactly one acceptance criterion in its `AC-Ref` column, and every acceptance criterion has at least one example.                                                                                                                                                                                                                                                                                                                                    |
| BR inside a contract | A business rule written inside the contract file that enforces it, with the fields `id`, `statement` and `examples`: an `x-qfai-rules` extension in a YAML contract, `-- Rule` comment lines in a SQL contract, a `## Rules` table in a Markdown contract. A rule spanning contracts lives in the authoritative one, and the others cite its ID. ID `BR-NNNN`, numbered across all contracts. Every BR cites at least one EX, and every EX is cited by at least one BR. |
| `decisions.md`       | The project-wide decision table at `.qfai/spec/decisions.md`. Four columns: ID, Content, Approach, Status. ID `DEC-NNNN`. Status is TODO, WIP, DONE, SUPERSEDED (by `DEC-NNNN`) or REJECTED. Rows are appended, and only Status changes. Holds triage records, change requests, retired stories and test exceptions. A row a validator reads opens its Content with `Test exception:` or `Change request:`; Status alone decides whether it is in force.                |
| `open-questions.md`  | The project-wide open-question table at `.qfai/spec/open-questions.md`. The same four columns. ID `OQ-NNNN`. Status is TODO, WIP, DONE or DEFERRED. A row opening `Unadjudicated:` is read as an unadjudicated question while its Status is TODO or WIP. Not an OQ in a discussion pack, which belongs to that pack.                                                                                                                                                    |
| test exception       | A `decisions.md` row opening `Test exception:`, then the BF, AC or EX IDs it exempts, with the reason in Approach. It holds only while DONE. It exempts only the obligation its ID's shape carries — a BF its E2E test, an AC its integration or API test, an EX its test — and does not reach the BF's stories or the AC's examples.                                                                                                                                   |
| `rule/`              | `.qfai/assistant/rule/`: the home of an assistant file that several skills use or the CLI reads, such as `constitution.md`, `communication.md` and `test-layers.md`. A file one skill uses goes to that skill's `references/` instead. `constitution/`, `catalog/` and `manifest/` are removed once emptied. Not `.agents/rules/`, which holds the rules every AI coding agent follows.                                                                                 |

### Intent-driven entry (2026-09-26)

| Term              | Definition                                                                                                                                                                                                                                                  | Not the same as                                                         |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| run               | One operator request carried through `npx qfai workflow`, from `start` to a terminal state. Its runtime state and tracked evidence are laid out in `03_contract/cli/workflow-files.md`; its states are in `03_contract/cli/qfai-workflow.md#state-machine`. | -                                                                       |

| obligation set    | The BF, AC and EX IDs of the business flow a run binds, with whether a test annotates each example. A stage of a run processes the examples no test annotates.                                                                                              | A ledger: nothing records the set apart from the tree and the tests     |
| route (workflow)  | The workflow a change request takes, resolved to a plan the package ships (`workflow-files.md#plan-files`).
