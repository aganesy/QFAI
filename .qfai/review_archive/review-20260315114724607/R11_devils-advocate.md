# R11: Devil's Advocate

## Verdict: PASS

## Premise: "Everything is wrong as it stands."

## Checklist

- [x] 「毎回調査」方式の実効性を疑う: 調査結果の品質保証メカニズムがあるか -> 検証済み、下記 Finding 1 参照
- [x] HTML+CSS Mock のスケーラビリティを疑う: 画面数が 50+ になった場合に破綻しないか -> 検証済み、下記 Finding 2 参照
- [x] Design Token 3 点セット「必須」の妥当性を疑う: 過剰要求ではないか -> 検証済み、下記 Finding 3 参照
- [x] 「すべて同等に最重要」のトレードオフ回避を疑う: 現実的に成立するか -> 検証済み、下記 Finding 4 参照

## Findings

### Challenge 1: 「毎回調査」は品質が不安定になる

**主張**: OQ-0002 で「ベストプラクティスを毎回調査し永続保存しない」と決定しているが、調査の品質は LLM のコンテキストや調査時点のインターネット情報に依存する。同じプラットフォーム・同じ FW でも、調査タイミングによって異なる結果が出る可能性がある。これはレビューの再現性（NFR-0010）と矛盾する。

**あるべき姿**: 調査結果を discussion-pack 内に記録する方式（OQ-0002 の決定通り）であれば、その discussion のスコープ内では再現性が保たれる。NFR-0010 は「同一の成果物に対して同一のルールセットで実行」と定義されており、ルールセットが discussion-pack に記録される限り矛盾しない。

**評価**: 設計上の矛盾は回避されている。PASS。ただし SDD で「調査結果の記録フォーマット」を明確に定義すべき。

### Challenge 2: HTML Mock は画面数増加で管理不能になる

**主張**: 03_Story-Workshop の HTML mock は 1 画面で約 50 行のインライン HTML。画面数が 30+ になれば Story Workshop だけで 1500+ 行になり、レビュー不能になる。さらに状態バリアント（5 種）を掛けると 7500+ 行。

**あるべき姿**: discussion 段階では「代表的な画面パターン」のみを Example Seed として示すのが目的であり、全画面網羅は SDD/spec-pack の役割。03_Story-Workshop の mock は List View / Form / Empty State の 3 パターンを例示しており、discussion の目的に合致している。SDD 段階では画面ごとに個別ファイル（`mocks/screen-xxx.html`）に分離すべき。

**評価**: discussion 段階の scope として適切。PASS。

### Challenge 3: 3 点セット「必須」は過剰要求

**主張**: QP-01 で「UI 要件が存在する場合、3 点セット必須」としているが、単純な設定画面や確認ダイアログにまで Design Token + HTML Mock + Mermaid を要求するのは過剰。開発速度を著しく低下させる。

**あるべき姿**: QP-01 は「UI 要件が存在する場合」という条件付きであり、すべての画面に適用するわけではない。また、QP-03 で状態バリアントは「推奨」（Must ではなく Should 相当）としている。discussion 段階では方針定義であり、具体的な適用基準は SDD で refined される。

**評価**: 方針としては妥当。SDD でスクリーンの複雑度に応じた適用レベル（Full / Minimal / Skip）を定義すれば運用可能。PASS。

### Challenge 4: 「すべて同等に最重要」は意思決定の放棄

**主張**: OQ-0007 で「正確性・柔軟性・整合性はすべて同等に最重要。実装コストは二の次」としているが、これは「優先順位を決めない」と同義。実装段階で衝突が発生した場合の判断基準がない。

**あるべき姿**: discussion 段階では理想的な方針を掲げることは許容される。User が Product Owner として「コスト度外視で品質追求」を明示的に決定しており、これは Valid な PO 判断。実装段階で具体的な衝突が発生した場合は、その時点の OQ として扱えばよい。

**評価**: PO の明示的判断として尊重すべき。PASS。

### Challenge 5: プラットフォーム非依存は幻想

**主張**: OQ-0008 で「あらゆるプラットフォームに対応」としているが、HTML+CSS Mock は本質的に Web 技術。Windows ネイティブ (WPF/WinUI) や iOS (SwiftUI) のアプリに対して HTML mock で見た目を定義するのは抽象度のミスマッチ。

**あるべき姿**: 03_Story-Workshop の HTML mock はあくまで「ビジュアル意図の伝達手段」であり、「実装対象の技術」ではない。Figma のモックアップがプラットフォーム非依存であるのと同じ原理。Design Token YAML は `platform: web | windows | mobile-ios | mobile-android` フィールドを持ち（REQ-0002）、プラットフォーム固有の値変換を定義できる。HTML mock は「こう見えるべき」の伝達、Token YAML は「プラットフォーム固有の値マッピング」を担当する分業。

**評価**: 懸念はあるが、設計上のレイヤー分離で対応可能。PASS。ただし、SDD で「非 Web プラットフォーム向け mock の代替表現」を検討すべき。

### Challenge 6: 消費プロトコルが抽象的すぎる

**主張**: REQ-0014 で「UI 定義消費プロトコルを定義する」としているが、03_Story-Workshop には消費プロトコルの具体的な手順やフォーマットが記述されていない。下流 skill がどの順番で何を読み、どう解釈するかが不明。

**あるべき姿**: discussion 段階では「消費プロトコルが必要である」という要件の確立が目的であり、具体的なプロトコル仕様は SDD の担当範囲。REQ-0014 に「読み取り順序、優先度、フォールバック規則を含む」と明記されており、SDD での具体化が約束されている。

**評価**: discussion 段階の粒度として適切。PASS。
