### ISSUE-01: 「ゆるやかな責務分離」は曖昧さを設計原則に格上げした欺瞞である

**対象**: 02_Inception-Deck Q10、05_Scope §6、08_Glossary「ゆるやかな責務分離」、OQ-0011

**主張**:
「ゆるやかな分離」という言葉は一見、柔軟性・協調を美徳として提示しているが、実態は「誰が担当するか不明確な領域を意図的に放置している」ことの言い換えに過ぎない。

フォーム設計を例に取ると、このパックは「UX Expert とDesign Expert が協調して担当」と書くが、協調の優先順位・意思決定ルール・コンフリクト解決プロセスが一切定義されていない。「ゆるやかな分離 + 統合レビュアーが最終調整」と言っているが、統合レビュアーが調整するタイミングは「最終レビュー時」であり、それ以前の作業フェーズでの重複・競合・抜け漏れを防ぐ仕組みが何もない。

4専門家が各自「全フェーズ」で関与する場合、各専門家が独立してリサーチを行い、独立して成果物を出す。それらが矛盾した場合、統合レビュアーが「修正指示」を出すことになるが、修正は誰が行うのか？修正した後、他の専門家の成果物との再整合をどう担保するのか？このループは明示されていない。

「ゆるやかな分離」を採用した理由（OQ-0011 代替案 A 棄却理由）は「完全分離では重複領域のカバーが困難」とされているが、これは逆説的だ。重複領域をカバーするためにあえて境界を曖昧にするのであれば、それは設計の失敗を先送りにしているだけである。

**代替案（あるべき姿）**:
責務分離を「ゆるやか」ではなく「一次責務 + 協議権」モデルで定義すること。具体的には、各成果物の項目ごとに一次責務者（Primary Owner）を明確に指定し、他の専門家は「レビュー・コメント権」のみを持つ。コンフリクト発生時は一次責務者が最終決定権を持ち、その判断の根拠を OQ として記録する。統合レビュアーは「事後調整者」ではなく「コンフリクト記録の検証者」として機能する。例：フォーム設計の一次責務 = Design Expert（ビジュアル構造）、UX Expert は認知負荷の観点から協議権を持つ、として明文化する。

### ISSUE-02: Research-First Protocol は「必須」と書いてあるだけで、未達時の検知・差し止め機構が存在しない

**対象**: 02_Inception-Deck Q10 Research-First Protocol、06_REQ REQ-0023、07_NFR NFR-0011

**主張**:
「作業冒頭でベストプラクティス/アンチパターンのリサーチを必須実施する」と全15ファイルで繰り返し強調されているが、「必須」であることを保証するメカニズムが一切存在しない。

NFR-0011 は「リサーチ項目のソース明記率 100%、直近 2 年以内の情報参照率 ≥ 80%」を測定基準として挙げるが、これはリサーチが「実施された後」の品質チェックに過ぎない。リサーチを省略してもシステムは止まらない。エージェントがリサーチを完了せずに作業を開始した場合に、どのコンポーネントがどのタイミングで検知し、どのように止めるのか、一切記述がない。

OQ-0002 で「ベストプラクティスの永続保存をしない」と決定されているため、直前のリサーチ結果がなければ専門家は参照すべきナレッジを持たない状態で動作することになる。これは「必須」ではなく「努力目標」であり、ドキュメント上の「必須」という言葉がシステム的に強制されていない以上、有名無実の制約である。

REQ-0023 は「リサーチプロトコルの定義」を要件とするが、プロトコル定義の達成基準が「定義する」という動詞で終わっており、「強制される」「検証される」という動詞がない。

**代替案（あるべき姿）**:
Research-First Protocol に Gate 機能を組み込むこと。具体的には、各専門家サブエージェントの作業セッション開始時に「リサーチ完了チェックポイント」を設け、リサーチ出力（最低限：プラットフォーム名、参照ソース3件以上、ベストプラクティス要約、アンチパターン要約）が存在しない場合は後続の定義作業をブロックする。REQ-0023 の達成基準に「研究チェックポイント通過なしで後続タスクを実行した場合は validate エラーとする」を明示する。NFR-0011 の測定基準に「リサーチ Gate 通過率 100%（省略ゼロ）」を追加する。

### ISSUE-03: 統合レビュアーを review-roster の13番目に置くことは、評価の独立性を構造的に破壊する

**対象**: 01_Context Stakeholders、02_Inception-Deck Q10、OQ-0013、11_OQ-Register

**主張**:
統合レビュアーは「4専門家の成果物を統合的にレビューする」と定義されている。しかし統合レビュアー自身も「作業冒頭でベストプラクティス/アンチパターンのリサーチを必須実施」する専門家サブエージェントでもある（01_Context Stakeholders、02_Inception-Deck Q10）。

つまり、統合レビュアーは「専門家として成果物の生成に関与するフェーズ」と「review-roster のメンバーとしてその成果物を評価するフェーズ」の両方に存在する。これは構造的な利益相反である。自分が（間接的に）形成に関与した成果物を自分でレビューすることは、独立した評価とは言えない。

OQ-0013 の棄却オプション C（「既存 ui-ux-reviewer を置き換え」）を棄却した理由は「既存レビュアーの専門性が失われる」だが、今回採択されたオプション B（13番目に追加）は、統合レビュアーの独立性問題を全く検討していない。

さらに、review-roster に13番目として追加することで、レビューが「12名 + 自己評価的1名」という構造になっており、統合レビュアーのレビューが形式的なゴム印になるリスクがある。

**代替案（あるべき姿）**:
統合レビュアーの役割を「専門家フェーズ」と「レビューフェーズ」に厳密に分割すること。専門家フェーズでは、統合レビュアーは4専門家の成果物の「一貫性チェックアドバイザー」として機能し、成果物の生成には直接関与しない（生成は4専門家のみ）。レビューフェーズでは、統合レビュアーは自分が一切関与していない成果物のみをレビュー対象とする。あるいは、統合レビュアーを review-roster ではなく「事後統合検証フェーズ」の専用エージェントとして分離し、review-roster の13番目とはしない。

### ISSUE-04: 「全フェーズ活動」の定義が抽象的すぎて、フェーズ間の責務継承プロトコルがない

**対象**: 02_Inception-Deck Q10 活動フェーズ、06_REQ REQ-0025、OQ-0012

**主張**:
「全フェーズ（discussion, SDD, prototyping, ATDD）で各専門家が関与する」と OQ-0012 で決定されているが、フェーズをまたいだ際の「何を引き継ぐか」「どの成果物が次フェーズの入力になるか」「前フェーズの決定が後フェーズで覆された場合どうするか」が一切定義されていない。

REQ-0025 は「フェーズごとの活動内容（方針策定/詳細定義/実装品質担保/検証品質担保）を明確化」と書いているが、これは「どのフェーズで何をするか」の箇条書きであり、「どのように前フェーズから引き継ぎ、どのように次フェーズに渡すか」のプロトコルではない。

具体的リスク：SDD フェーズで Design Expert が Design Token スキーマを変更した場合、discussion フェーズで Screen Transition Expert が定義した Mermaid 画面遷移図は自動的に整合性を失う可能性がある。この場合、誰が検知し、誰が修正を指示し、誰が修正するのか？REQ-0025 にも NFR にも記述がない。

**代替案（あるべき姿）**:
フェーズ間に「ハンドオフプロトコル」を明示すること。各専門家はフェーズ完了時に「フェーズ成果物サマリー」（変更点・意思決定・次フェーズへの申し送り事項）を出力する義務を REQ として追加する。次フェーズ開始時に、専門家は前フェーズのサマリーを確認し、自分の作業との整合性をチェックする手順を定義する。また「フェーズ間整合性チェック」を qfai validate のルールとして追加し、Design Token・HTML Mock・Mermaid・UI Contract の四者間の不整合を自動検出する仕組み（既に REQ-0015 に存在するが、フェーズをまたいだ変更追跡に限定して強化する）。

### ISSUE-05: Research-First Protocol の「毎回実施」はコスト爆発と品質劣化を同時に引き起こす

**対象**: 02_Inception-Deck Q10 Research-First Protocol、OQ-0002、06_REQ REQ-0023、07_NFR NFR-0011

**主張**:
OQ-0002 で「ベストプラクティスは永続保存しない。毎回 /qfai-discussion で調査する」と決定されている。これを全フェーズ（OQ-0012）で活動する5専門家が全員実施するならば、1プロジェクトの1ディスカッション実行で5回のフルリサーチが走り、SDD フェーズでさらに5回、prototyping でさらに5回、ATDD でさらに5回、合計20回のリサーチが必須となる。

しかも、各リサーチは「対象プラットフォーム・ドメイン特化」であり、5専門家が同一のプラットフォームについて独立してリサーチするため、大量の重複情報が生成される。NFR-0011 は「直近2年以内の情報参照率 ≥ 80%」を要求しているが、毎回独立リサーチすることで「同じ情報源を5名が独立して参照し、5種類のフォーマットで記録する」という非効率が発生する。

さらに、リサーチ品質は調査タイミングと情報源の選択に依存するため、同一プロジェクトの異なるフェーズで矛盾する「最新」情報が記録される可能性がある。永続保存がないため、過去のリサーチとの比較もできず、リサーチ結果の漂流が起きる。

**代替案（あるべき姿）**:
Research-First Protocol に「リサーチキャッシュ」の概念を導入すること。プロジェクト単位でリサーチ結果を discussion-pack 内の専用ファイル（`00_Research-Cache.md`）に記録し、同一フェーズ内での重複実施を禁止する。異なるフェーズ間でのリサーチは、前回のキャッシュとの差分が確認できる新情報がある場合のみ再実施する（「差分リサーチ」）。5専門家が共有ベースラインとなるプラットフォーム共通リサーチを1回実施し、各専門家は自分の専門領域に特化した追加リサーチのみを行う「共有ベース + 専門特化追加」モデルを採用する。永続保存しないことの弊害（OQ-0002 棄却理由「時代遅れのルール」）は、キャッシュに有効期限（例：30日）を設けることで対処する。

### ISSUE-06: UI/UX Expert と Navigation Expert の責務範囲に実質的な重複があり、独立存在の正当性が疑わしい

**対象**: 01_Context Stakeholders、02_Inception-Deck Q10、08_Glossary

**主張**:
UI/UX Expert の責務は「ユーザビリティ評価・認知負荷分析・情報設計・インタラクション設計」とされている。一方、Navigation Expert の責務は「IA（情報アーキテクチャ）構造設計・メニュー/タブ/サイドバー設計・ブレッドクラム・導線最適化・ファネル設計」とされている。

情報設計（Information Architecture）は IA（情報アーキテクチャ）の中核であり、UI/UX Expert の「情報設計」と Navigation Expert の「IA 構造設計」は実質的に同一の領域を指している。さらに、導線設計・ナビゲーション構造はユーザビリティの直接的な構成要素であり、認知負荷分析なしに適切なナビゲーション設計は不可能だ。

つまり、UI/UX Expert と Navigation Expert は「同じ対象物を異なる抽象レベルで見ている」に過ぎず、「ゆるやかな分離」という方針の下では、両者が同一の成果物に対して重複したコメントを出し続けるリスクが高い。OQ-0011 の棄却オプション C（「2専門家に統合」）を棄却した理由は「専門性が薄まる」とされているが、4名全員を別々のエージェントとして維持することで得られる追加価値が、増大するコンテキスト管理コストと協調コストを上回る根拠が提示されていない。

**代替案（あるべき姿）**:
UI/UX Expert と Navigation Expert の責務を、「分析フェーズ vs 設計フェーズ」で再分割すること。UI/UX Expert は「ユーザー行動の分析・評価（ユーザーリサーチ、ユーザビリティテスト、認知負荷評価）」を担当し、Navigation Expert は「IA・ナビゲーション構造の設計・実装判断（メニュー構造、情報階層、導線最適化）」を担当する。情報設計は UI/UX Expert の分析結果を基に Navigation Expert が設計を行う、という明確な入出力関係を定義する。これにより重複をなくし、かつ4名体制の専門性を維持できる。あるいは、この2役を1名に統合し「UX Architect」として定義し直す。

### ISSUE-07: 「毎回リサーチ」と「プラットフォーム非依存設計」は思想的に矛盾している

**対象**: 01_Context Assumptions §3、OQ-0002、OQ-0008、06_REQ REQ-0023

**主張**:
Assumptions §3 は「UI/UX のベストプラクティスは時代とともに変化するため、固定的なルールセットではなく、都度調査・更新可能な設計とする」と主張する。OQ-0008 は「固定せず、状況に応じて都度情報収集する設計」と決定している。

しかし同時に、このシステムはプラットフォーム非依存（OQ-0008）を原則とし、「あらゆるプラットフォームに対応する」と宣言している。これらは両立しない。

プラットフォームが未確定な状態で「プラットフォーム特化のベストプラクティスを都度リサーチする」ことは、「何に対するリサーチなのか」が作業開始時点で決まらないことを意味する。QFAI を使う開発者がプロジェクト開始時にプラットフォームを明示しなかった場合、リサーチのスコープが確定できず、Research-First Protocol は機能しない。

NFR-0002 は「新プラットフォーム追加時のコア変更行数 = 0」を要求しているが、「コア変更なし」で「プラットフォーム特化リサーチ」を追加するとはどういう意味なのか？リサーチプロセス自体は「コア」ではないのか？この定義があいまいである。

**代替案（あるべき姿）**:
プラットフォームを「作業開始前に必ず明示する必須パラメーター」として定義し、プラットフォーム未指定の場合は専門家サブエージェントの起動をブロックすること。09_Constraints に「TC-06: 専門家サブエージェントの起動にはプラットフォーム指定が必須」を追加する。あわせて、「プラットフォーム不明の場合のフォールバック（共通ベストプラクティスのみ適用）」を明示的に定義し、その場合は Research-First Protocol の達成基準を下げる（例：「プラットフォーム指定ありの場合のみ NFR-0011 の 80% 基準を適用」）。

### ISSUE-08: 13_Deferred が完全に空であることは、リスク管理の形骸化を示している

**対象**: 13_Deferred.md

**主張**:
13_Deferred は「0 items」と記録されている。これを額面通りに受け取るならば、全 OQ は resolved であり、deferred 事項がゼロということになる。しかしこれは信用できない。

今回のドリフトで追加された機能は相当に大規模だ：5専門家サブエージェントの定義（REQ-0019〜REQ-0025）、Research-First Protocol の実装（REQ-0023）、統合レビュアーの review-roster 統合（REQ-0024）、全フェーズ活動定義（REQ-0025）。これらは SDD 以降で具体的なエージェント定義ファイル・プロトコル文書・validate ルール追加として実装されるはずだが、その実装詳細の「どこまで SDD で決めるか」が OQ として記録されていない。

例えば：

- 各専門家サブエージェントのエージェント定義ファイルはどのディレクトリに配置するか（`.qfai/assistant/agents/` 配下か、新設ディレクトリか）
- Research-First Protocol の出力フォーマット（REQ-0023 に「含む」と書いてあるが、フォーマット例が discussion 段階で未定義）
- 統合レビュアーの review-roster への追加が既存の `review-roster.yml` へのエントリ追加で完結するのか、新スキーマが必要なのか

これらは「SDD で決めれば良い」と暗黙的に後回しにされているが、13_Deferred に記録がない。deferred 事項がゼロということは、これらの判断が SDD ゲートなしで実装者の裁量に委ねられることを意味し、品質管理の空白地帯が生まれる。

**代替案（あるべき姿）**:
13_Deferred に以下の項目を明示的に記録すること：(1) 各専門家サブエージェントのエージェント定義ファイルの配置先・スキーマ（SDD ゲートで決定）、(2) Research-First Protocol 出力フォーマットの詳細仕様（SDD ゲートで決定）、(3) 統合レビュアーの review-roster.yml へのスキーマ追加要否（SDD ゲートで決定）。「deferred がゼロ」は「すべて解決済み」ではなく「後続ゲートへの記録委ねを明示的に選択した」場合に限り有効であり、現状は後者の意図が確認できない。

### ISSUE-09: HTML+CSS Visual Mock の「プラットフォーム非依存」宣言と実例のギャップが露呈している

**対象**: 03_Story-Workshop HTML+CSS Mock 例、06_REQ REQ-0004

**主張**:
03_Story-Workshop に掲載されている HTML+CSS Visual Mock のサンプルは、完全に Web/Desktop 向けのデザインだ（max-width: 1024px のテーブルレイアウト、マウスカーソル想定のホバー操作）。01_Context と 05_Scope は「プラットフォーム非依存（Web/Windows/Mobile）」を繰り返し主張しているが、サンプルは Windows アプリや Mobile アプリの UI を表現していない。

REQ-0006 は「レスポンシブバリアント（デスクトップ・タブレット・モバイル）を表現できる記法を定義する」とあり、これは Web アプリのレスポンシブデザインを指している。Windows デスクトップアプリ（WPF/WinUI）や iOS/Android ネイティブアプリの UI を HTML+CSS で表現することは、技術的に根本的に不適切だ。Windows アプリは px ではなく dpis で設計され、WinUI の Fluent Design は HTML/CSS の概念と直接対応しない。

プラットフォーム非依存を宣言しながら、定義手法が本質的に Web 中心であることは矛盾であり、「都度リサーチする設計」という逃げ道では解決できない構造問題だ。

**代替案（あるべき姿）**:
HTML+CSS Visual Mock の位置づけを「Web プロジェクト向けのデフォルト表現手法」として明示的に限定し、プラットフォーム固有の代替表現手法を並列に定義すること。例：Windows アプリは「WinUI XAML スニペット風の疑似コード」または「ASCII ワイヤーフレーム」を採用し、Mobile アプリは「SwiftUI/Compose 疑似コード」または「ASCII ワイヤーフレーム」を採用する。REQ-0004 の説明から「HTML+CSS」という限定を取り除き、「プラットフォームに適した視覚的モック表現（Web: HTML+CSS、Windows: XAML 疑似コード、Mobile: ASCII ワイヤーフレーム等）」と書き直す。05_Scope にもこの限定を明記する。

### ISSUE-10: US-D009/US-D010 の Example Seeds に「専門家間コンフリクト」の否定経路が浅すぎる

**対象**: 03_Story-Workshop US-D009 Example Seeds、US-D010 Example Seeds

**主張**:
US-D009 の Negative path は「専門家のリサーチ結果が相互に矛盾する場合（例: UX Expert は簡素さ推奨、Design Expert はリッチ表現推奨）→ 統合レビュアーが調整」としている。しかしこれは「誰が調整するか」だけ定義して「どのように調整するか」「調整の結果として誰が成果物を修正するか」「調整ログはどこに記録されるか」が全て空白だ。

US-D010 の Negative path は「個別 PASS だが統合すると UX の一貫性に問題 → 統合レビュアーが FAIL + 具体的修正提案」としているが、「具体的修正提案」の粒度・フォーマット・受け入れ基準が未定義だ。修正提案を受けた専門家が修正を拒否した場合のエスカレーションパスもない。

さらに、US-D009 Edge case「ゆるやかな分離 + 統合レビュアー」としか書かれておらず、本来なら Edge case として検討すべき「統合レビュアー自身がリサーチミスをした場合」「全専門家の成果物が互いに矛盾した場合（2者ではなく4者コンフリクト）」「統合レビュアーの判断に専門家が全員異議を唱えた場合」がない。

**代替案（あるべき姿）**:
US-D009 の Negative path に「コンフリクト解決プロセスの詳細」を Example Seed として追加すること：統合レビュアーが調整案を出力 → 関係専門家が調整案に対してコメント → 最終決定者ルール（Primary Owner 方式、あるいは多数決方式）で決定 → 決定を OQ として記録。US-D010 の Negative path には「修正提案の受け入れ基準」として「修正案が原因となる矛盾を解消していることを統合レビュアーが再確認する」ステップを追加する。また、「統合レビュアー自身が誤判断した場合のエスカレーション先（例：Orchestrator、または review-roster の他メンバーによる多数決）」を Edge case として追加する。
