> **言語**: 出力は全て日本語
>
> **目的**: 本セッションの変更をリモートへ push し、プロジェクトの PR テンプレートに準拠した Pull Request を作成する。

---

## 🚨 最重要: PR説明のフォーマット厳守

PR の説明（body）は、**必ず** プロジェクトの PR テンプレートのフォーマットに従うこと。

### Step 0: PR テンプレートの読み込み（必須）

**PR作成前に必ず以下を実行し、テンプレートを取得すること**:

```bash
# PRテンプレートの確認（存在する場合）
cat .github/PULL_REQUEST_TEMPLATE.md 2>/dev/null || \
cat .github/pull_request_template.md 2>/dev/null || \
cat docs/pull_request_template.md 2>/dev/null || \
echo "テンプレートなし"
```

- [ ] テンプレートの内容を確認した
- [ ] テンプレートの構造（セクション、必須項目）を把握した

**テンプレートが存在する場合**: そのフォーマットに**完全準拠**すること。セクションの追加・削除・変更は禁止。

**テンプレートが存在しない場合**: 以下の最小構成を使用:

```markdown
## 概要

[変更内容の説明]

## テスト

[テスト方法・項目]
```

## 🎯 完了条件

- [ ] `/push` 相当の手順が完了している（コミット＋push成功）
- [ ] PR が GitHub 上に作成されている
- [ ] PR の説明がプロジェクトの PR テンプレートに完全準拠している
- [ ] PR タイトルが変更内容を端的に表している

## 📋 実行手順

### Step 1: Push

`.claude/prompts/push.md` が存在する場合はその手順を実行。存在しない場合:

```bash
git status --porcelain
git push
```

- [ ] 未コミットの変更がある場合はコミット
- [ ] `git push` が成功

---

### Step 2: デフォルトブランチの特定

```bash
# デフォルトブランチを取得
DEFAULT_BRANCH=$(git symbolic-ref refs/remotes/origin/HEAD 2>/dev/null | sed 's@^refs/remotes/origin/@@')
if [ -z "$DEFAULT_BRANCH" ]; then
  DEFAULT_BRANCH=$(git remote show origin | grep 'HEAD branch' | awk '{print $NF}')
fi
echo "デフォルトブランチ: $DEFAULT_BRANCH"
```

- [ ] デフォルトブランチを確認（以降の手順で使用）

---

### Step 3: PR 作成の事前確認

```bash
git branch --show-current
gh pr list --head $(git branch --show-current)
```

- [ ] 現在のブランチを確認
- [ ] 既存 PR がないことを確認（既存がある場合は Step 6 へスキップ）

---

### Step 4: 変更内容の収集

以下の情報を収集し、PR 説明の素材とする。

```bash
# マージ先ブランチとの差分コミット（$DEFAULT_BRANCH は Step 2 で取得した値）
git log origin/$DEFAULT_BRANCH..HEAD --oneline

# 変更ファイル一覧
git diff origin/$DEFAULT_BRANCH --name-only

# 変更の統計
git diff origin/$DEFAULT_BRANCH --stat
```

**収集すべき情報**:

| 項目           | 内容                                        |
| -------------- | ------------------------------------------- |
| 変更の目的     | なぜこの変更が必要か（背景・課題）          |
| 変更内容の要約 | 何を変更したか（機能/修正/リファクタ等）    |
| 影響範囲       | どこに影響するか（コンポーネント/API/DB等） |
| テスト実施内容 | どのようにテストしたか/すべきか             |
| 関連 Issue     | 関連する Issue 番号（あれば）               |
| 特記事項       | レビュアーに伝えるべき注意点（あれば）      |

---

### Step 5: PR 説明の作成

**Step 0 で取得したテンプレートに従って PR 説明を作成する。**

テンプレートの各セクションに対して:

1. セクション見出しをそのまま使用（変更禁止）
2. コメント（`<!-- ... -->`）の指示に従って内容を記入
3. チェックボックスがある場合は具体的な項目に置き換え
4. 空のセクションを作らない（該当なしの場合も「なし」等を記入）

---

### Step 6: PR 作成コマンドの実行

```bash
gh pr create \
  --title "[タイトル]" \
  --body "[Step 5で作成した説明]"
```

**タイトルの付け方**:

| パターン     | 例                                          |
| ------------ | ------------------------------------------- |
| 新機能       | `feat: ユーザー検索機能を追加`              |
| バグ修正     | `fix: ログイン時のエラーハンドリングを修正` |
| リファクタ   | `refactor: 認証ロジックを共通化`            |
| ドキュメント | `docs: セットアップ手順を追記`              |
| テスト       | `test: ユーザーサービスのテストを追加`      |
| 設定         | `chore: ESLint設定を更新`                   |

---

### Step 7: 作成結果の確認

```bash
gh pr view --web
```

- [ ] PR が正しく作成されている
- [ ] 説明がテンプレートに準拠している
- [ ] タイトルが適切

---

## 🔴 やってはいけないこと（禁止事項）

| カテゴリ         | 禁止内容                                         |
| ---------------- | ------------------------------------------------ |
| テンプレート違反 | PR テンプレートのセクションを省略・変更・追加    |
| テンプレート無視 | Step 0 でテンプレートを読まずに PR 説明を作成    |
| 情報不足         | 必須セクションに内容が書かれていない             |
| テスト未記載     | テスト関連セクションにテスト項目が1つもない      |
| 巨大PR           | 1つのPRに無関係な複数の変更を混ぜる              |
| 曖昧なタイトル   | 「修正」「更新」「変更」など具体性のないタイトル |
| WIP放置          | 作業中のまま正式PRとして作成                     |
| ドラフト無視     | 未完成なのにドラフトPRを使わない                 |

---

## 🟢 やるべきこと（推奨事項）

| カテゴリ           | 推奨内容                                                |
| ------------------ | ------------------------------------------------------- |
| 小さなPR           | 1つのPRは1つの目的に絞る（レビューしやすさを優先）      |
| 明確な説明         | レビュアーが変更の背景・目的を理解できる説明を書く      |
| 具体的なテスト     | 実施したテストと今後実施すべきテストを明記              |
| コンテキスト提供   | 関連するIssue、設計ドキュメント、議論へのリンクを含める |
| 自己レビュー       | PR作成前に自分でdiffを確認し、不要な変更を除去          |
| スクリーンショット | UI変更がある場合は変更前後のスクリーンショットを添付    |
| ドラフト活用       | 未完成・レビュー不要の段階ではドラフトPRを使う          |

## 📊 報告フォーマット

```markdown
## PR作成結果

- ブランチ: <branch>
- PR番号: #<number>
- タイトル: <title>
- URL: <url>

## 作成したPR説明

[実際に作成したPR説明を表示]
```

---

## ⚠️ エラーハンドリング

| 状況                   | 対応                                                    |
| ---------------------- | ------------------------------------------------------- |
| push 失敗              | エラー内容を確認し、原因を報告（権限、競合等）          |
| PR 既存                | 既存 PR の URL を報告し、更新が必要か確認               |
| gh コマンド未認証      | `gh auth login` の実行を案内                            |
| マージ競合の可能性     | `git fetch && git rebase origin/$DEFAULT_BRANCH` を提案 |
| テンプレート読込失敗   | 最小構成テンプレートを使用                              |
| デフォルトブランチ不明 | `main` または `master` を試行                           |

---

## 🔧 オプション: ドラフトPR作成

作業途中でフィードバックが欲しい場合:

```bash
gh pr create \
  --title "[WIP] [タイトル]" \
  --body "[PR説明]" \
  --draft
```

---

## 🔧 オプション: レビュアー指定

特定のレビュアーを指定する場合:

```bash
gh pr create \
  --title "[タイトル]" \
  --body "[PR説明]" \
  --reviewer @username
```

---

## 📚 参考: 良いPRの特徴

1. **小さく焦点を絞る**: 1つの目的に集中し、レビューしやすいサイズに保つ
2. **コンテキストを提供**: 変更の「なぜ」を説明し、レビュアーの理解を助ける
3. **テスト可能**: どうテストするかが明確で、再現可能
4. **セルフレビュー済み**: 作成者自身がdiffを確認し、品質を担保
5. **コミットが整理されている**: 論理的なコミット単位で、メッセージも明確
